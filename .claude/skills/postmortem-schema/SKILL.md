# Postmortem Schema

## 원칙: 미래의 검색어를 상상하고 쓴다
기록은 읽히려고 있는 게 아니라 **검색되려고** 있다.
6개월 뒤의 나(또는 다른 프로젝트의 에이전트)가 무슨 문자열로 이걸 찾을지 생각하고,
그 문자열이 본문에 실제로 들어가게 쓴다. 에러 메시지 원문, 라이브러리명+버전, 명령어를 반드시 포함한다.

## incident 섹션
| 섹션 | 쓰는 법 | 안 좋은 예 |
|---|---|---|
| symptom | 관측된 현상 + **에러 원문** + 재현 조건 | "빌드가 깨짐" |
| rootCause | 왜 그랬는지. 추정이면 추정이라고 명시 | "설정 문제" |
| resolution | 실제로 한 조치를 **명령어/코드 수준**으로 | "고침" |
| prevention | 재발 방지책. 없으면 "없음"이라고 쓴다 | (공란) |

## divergence 섹션 (이 시스템의 고유 가치)
AI 에이전트 산출물이 의도와 벌어진 사건. 일반 버그와 구분해 기록한다.

| 섹션 | 쓰는 법 |
|---|---|
| expected | 내가 의도한 것 / 스펙에 있던 것 |
| actual | 에이전트가 실제로 만든 것 (환각한 API명, 잘못 가정한 버전 등 구체적으로) |
| context | `model`, `tool`, `framework` — **재현 조건이 없으면 지식이 아니다** |
| correction | 어떻게 교정했는가: 프롬프트 수정? 스펙 문구 보강? 스킬 신설? |

`correction`이 가장 중요하다. 이 필드가 다음 프로젝트의 CLAUDE.md·스킬로 환류된다.
"다시 지시했더니 됐다"는 correction이 아니다. **무엇을 명시했더니 됐는지**를 쓴다.

## 길이
섹션당 3–10문장. 너무 짧으면 검색이 안 되고, 너무 길면 청크가 쪼개져 정확도가 떨어진다.

## 공개 자료 인용
외부 포스트모템을 시드로 쓸 때 **원문을 복제하지 않는다.** 자기 문장으로 요약하고 출처 URL을 남긴다.

## 시크릿
넣지 않는다. 새니타이저가 잡지만 의존하지 않는다.
