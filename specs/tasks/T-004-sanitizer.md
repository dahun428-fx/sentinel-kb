# T-004: sanitizer (시크릿 마스킹 + 인젝션 플래그)

STATUS: 6차 패스 — N-10(mongo 자격증명 미탐 7종) 종결. `pnpm verify` 그린.

> **⚠️ 절차 기록 — 재시도 한도를 두 번 넘겼다.**
> task-loop 프로토콜의 재시도 한도는 3회다. 4차에서 이미 한 번 넘겼고(그때 검증자가
> BLOCKED 대신 한정 패스를 권고했으나 그 판단의 전제가 틀렸음이 드러나 BLOCKED로 마킹했다),
> 이번 5차가 **두 번째 초과**다.
>
> **해제 결정 주체: 오케스트레이팅 에이전트(자율 판단, 2026-08-22).** 인간 승인이 아니다.
> 근거: 남은 항목이 파괴적 작업도 스코프 변경도 아닌 **기술 설계 선택**이었고,
> 이 레포에서 스펙 결함 20건 가까이를 같은 방식(에이전트가 결정 → 근거와 함께 비준 대기열에 등재)으로
> 처리해 온 전례와 일관된다. **인간 사후 비준 대상이며, 비준 시 이 절차 자체도 함께 판단해 주기 바란다.**

해제 근거: 네 결정이 내려졌고 그대로 구현했다. 미탐과 오탐을 **동시에** 닫았다.
  1. mongo 자격증명을 URI **구조 파싱**으로 교체 — N-8(점 없는 호스트 유출)과
     F-15(정상 문장의 호스트 삭제)가 동시에 닫혔다. 결정 1의 케이스 11종 전부 기대대로.
  2. 프로브 비가시 집합을 `\p{Cf}`·`\p{Cc}` 범주 전체로 확대 — N-9 29종 종결.
     `Cs`(짝 없는 서로게이트)는 결정 3의 생성기가 새로 찾아내 함께 닫았다.
  3. 프로퍼티 생성기를 구현에서 독립 — General_Category 열거 + 전 평면 무작위 표집.
     `\p{Cf}` 확대를 되돌리면 **프로퍼티가 죽는다**(구 생성기에서는 통과했다). F-17 종결.
  4. `SANITIZE_MAX_INPUT_CHARS`(기본 65536) 도입 — 초과 시 `SanitizeInputTooLargeError`.

  **결정 2의 부수 효과(기록):** `IGNORABLE_RE` 확대는 마스킹 프로브뿐 아니라
  `injection.ts`의 `toProbe()`에도 그대로 적용된다. 방향은 회피 저항 강화라 무해하지만,
  F-9가 "두 집합을 의도적으로 다르게 유지한다"고 선언한 모듈이므로 명시해 둔다.
  넓히지 않은 것은 **인젝션 "과도한 제로폭" 계수**(`ZERO_WIDTH_RE`)뿐이다 —
  U+FE0F가 이모지 표현 선택자라 넓히면 이모지 4개가 든 정상 기록이 오탐된다.

## Findings

### T-002 F-5 종결 — `SanitizeFlag` 2종으로 확정
specs/02:31이 `sanitizeFlags: string[]`이지만 **주석이 값 집합을 2종으로 못박고 있어**
`string[]`은 JSON 표기상의 느슨함이지 확장 허가가 아니다. contracts의 `z.enum`이 같은 집합을
더 정확히 표현한 것이고, T-004가 실제로 2종만 생산함이 테스트로 확정됐다.
**F-5는 보류가 아니라 확인으로 해소됐다.**

가변적인 축(마스킹 종류 6개)은 `MaskKind`로 core에 격리해 계약 표면에 올리지 않았다.
**3번째 플래그를 추가하려면 스펙 개정 + 기존 레코드 마이그레이션이 동반돼야 한다** —
읽기 경로에서 `RecordSchema`로 재검증되므로 실제로 파싱이 깨진다.

### T-007·T-015·T-021의 선행 조건 (반드시 먼저 처리)
- **F-1 `sanitize()`가 마스킹 종류와 규칙 id를 버린다.** 공개 계약이 `{text, flags}`뿐이라
  specs/07 §3("마스킹이 발생하면 **무엇이 마스킹됐는지 알려준다**, 조용히 삼키지 않음")을
  T-007이 채울 수 없다. 남은 길은 둘 다 나쁘다 — 본문 라벨 `[MASKED:...]`을 **재파싱**하거나,
  `applyMasking()`+`detectInjection()`을 API 계층에서 **재조립**해 게이트의 단일 진입점을 깨는 것.
  **T-002 F-6(`warning`이 갈 곳이 없다)과 같은 문제의 양면이며 T-007에서 동시에 결정해야 한다.**
  필요한 것은 contracts 변경이 아닌 core 내부 확장:
  `SanitizeResult { text, flags, masked: readonly MaskKind[], injectionRules: readonly string[] }`
- **F-2 `MaskKind`가 HTTP 응답에 실리는 순간 계약 표면이 된다.** 그때는 contracts로 옮겨야 한다.
  지금은 core 내부 개념이라 위반이 아니다.
- **F-3 T-021이 규칙 id를 못 쓴다.** `detectInjection()`은 id를 반환하지만 `sanitize()`가 버리므로
  저장 경로 어디에도 남지 않는다. Eval 4 리포트에 "어떤 회피 수법이 몇 건인지"가 안 실리고
  규칙 회귀(어떤 id가 죽었는지)를 진단할 수 없다. 규칙 id 목록도 export되지 않아
  기대 집합을 열거할 수 없고, `zero-width-abuse`만 `INJECTION_PATTERNS` 밖에서 합성돼 id 출처가 이원화됐다.
  F-1의 `injectionRules` 확장이 이 둘을 동시에 해결한다.

### 미해결
- **F-4 `sanitize()`가 옵션 미지정 시 `process.env`를 직접 읽는다.**
  **5차 갱신:** G5가 `resolveOptions`의 "둘 다 주어졌을 때만 env를 건너뛴다" 구조를
  **회귀로 지적했으나, 검증해 보니 동작 차이가 없다.** `??`가 단락 평가하므로 두 구현의
  **출력이 동일**하고, 차이는 `process.env`를 몇 번 읽느냐뿐이다. 뮤테이션으로 확인했다 —
  옛 구조로 되돌려도 142개 테스트가 전부 통과한다(**동등 뮤턴트**).
  그럼에도 필드별 독립 해석으로 바꾼 이유는 **의도가 코드에 드러나기 때문**이다:
  "명시된 필드는 env를 조회하지 않는다"가 구조로 보인다. 회귀 테스트 3개는 그 계약을 문서화한다
  (동작이 같으므로 뮤턴트를 죽이지는 못한다 — 그 사실도 여기 적어 둔다).
  **원래 F-4(`sanitize()`가 옵션 미지정 시 env를 직접 읽는다)는 여전히 미해결이다.**
  T-007은 컴포지션 루트에서 옵션을 한 번 만들어 항상 명시적으로 넘겨야 한다.

  주변 env에 따라 같은 입력이 다른 출력을 낼 수 있다.
  T-007은 컴포지션 루트에서 `readSanitizeOptions()`를 한 번 부르고 옵션을 항상 명시적으로 넘길 것.

### 수정 라운드에서 새로 발견 (B-1~B-8 수정 후)

- ~~**F-8 제로폭 집합이 좁아 같은 계열 미탐이 남아 있다.**~~ **해소됨.**
  마스킹 프로브가 Unicode `Default_Ignorable_Code_Point` 전체를 지우도록 넓혔다.
  soft hyphen(U+00AD)·CGJ(U+034F)·variation selector(U+FE00–FE0F)·tag 문자(U+E0000–E007F)가
  전부 덮인다. 한글·한자와 정상 결합 악센트는 이 속성이 아니라 영향받지 않는다.
  후행 흡수도 코드유닛이 아닌 **코드포인트** 단위로 고쳤다 — tag 문자는 서로게이트 쌍이라
  반쪽만 보면 잔여물이 남았다. 5종 + astral 후행 케이스를 회귀 테스트로 잠갔다.
- ~~**F-9 정규화 로직 두 벌.**~~ **해소됨.** `sanitizer/invisible.ts`가 단일 소스다.
  다만 **두 집합을 의도적으로 다르게 유지**하고 근거를 나란히 적었다:
  마스킹 프로브는 `Default_Ignorable` 전체(미탐이 유출이므로 넓게),
  인젝션 "과도한 제로폭" 계수는 진짜 폭 없는 문자만(좁게).
  계수까지 넓히면 **U+FE0F가 이모지 표현 선택자라 이모지 4개가 든 정상 기록이 오탐**된다.
  인젝션 플래그는 지식을 지우진 않지만 검색 노출과 생성 컨텍스트 제외에 영향을 준다(specs/03 §2).

- **F-10 앵커 규칙이 `api_key` 계열만 본다.** `ANTHROPIC_AUTH_TOKEN=`, `*_TOKEN=`,
  `password=`, `*_SECRET=` 앵커는 커버하지 않는다(실측 LEAK). F-5(미커버 유출 벡터)와
  같은 축이며 Scope 열거 밖이라 이번에도 넣지 않았다. T-007 이전에 함께 판단할 것.
- **F-11 `applyMasking`의 겹침 해소가 세그먼트 수에 대해 이차다**(`chosen.some`).
  100KB 실측에선 문제없으나 시크릿이 수천 개 박힌 입력에선 비용이 튄다.
- **F-12 mongo 규칙이 한쪽만 마스킹할 때 라벨이 user/pass를 구분하지 못한다.**
  `<user>:[MASKED:db-credentials]@`에서 가려진 것이 비밀번호라는 사실이 라벨에 없다.
  F-1의 구조화된 `masked` 확장이 해결할 축과 같다.

### specs/03 §6(하드코딩 금지) 위반 아님 — 판정 근거
§6의 사유는 **"eval에서 스윕하기 위함"**이고 대상은 `RETRIEVAL_*`·`RRF_K`·`SIMILARITY_THRESHOLD`처럼
품질 지표와 트레이드오프하는 노브다. 새니타이저 임계값(키 본문 20자, 제로폭 3, Bearer 8자, AWS 40자)은
**정규식의 형태 규격이자 보안 정확도 상수**로, eval이 스윕할 대상이 아니다.
오히려 env로 빼면 **오설정이 마스킹을 조용히 무력화하는 보안 회귀 경로**가 생긴다.
`SANITIZE_MASK_EMAIL`만 env인 것은 일관적이다 — 이건 임계값이 아니라 정책 토글이고
Scope가 유일하게 "(옵션)"으로 표시한 항목이다.

### 2차 재검증에서 나온 것 — 수정 완료
- **N-1 (F-8 수정이 만든 거울상 구멍).** 프로브가 비가시 문자를 *삭제*하므로 시크릿 **경계**에
  있던 문자가 옆 토큰을 시크릿에 붙여 `\b` 앵커를 깼다. `AKIA…EXAMPLE<ZWSP>x`가
  **플래그도 마스킹도 없이** 통과했다(제로폭 1개는 인젝션 임계값 이하).
  원문에 직접 돌리면 잡히는데 프로브에서는 안 잡히는, 정확히 F-8과 반대 방향의 실패다.
  → **두 좌표계(프로브 + 원문) 모두에서 구간을 모아 합집합**을 취하고, 겹치면 더 넓은 쪽을 남긴다.
- **N-2 U+2800 BRAILLE PATTERN BLANK.** 점 없는 점자 블록이라 공백으로 보이지만
  Unicode 속성이 `Lo`라 `Default_Ignorable`에 안 잡힌다. 한글 채움 문자와 함께 명시 열거했다.
- **N-3 mongo userinfo의 공백.** 문자 클래스가 공백을 배제해 `<db user name>:진짜비번@host` 처럼
  한쪽에 공백이 든 순간 **규칙 전체가 무발동해 비밀번호까지 통과**했다. B-2가 고친 케이스의 바로 옆 변형이다.
  → 개행만 배제하고 길이를 `{1,128}`로 묶었다.
- **N-4 결합 표시(U+0301 등).** 프로브가 NFKC라 선조합 `Á`(U+00C1)는 분해되지 않았다.
  → **NFKD로 분해한 뒤 `\p{Mn}` 제거**. 조합형·선조합 양쪽이 같은 경로로 처리된다.
- **M10/M12 가짜 커버리지.** "과도한 제로폭"은 Scope 명시 패턴인데 **규칙을 통째로 지워도
  전 테스트가 그린**이었다. 기존 케이스가 제로폭이 든 `ignore previous instructions`라
  프로브가 제로폭을 지운 뒤 다른 규칙이 먼저 매치돼 계수가 판정에 기여하지 않았다.
  → 다른 어떤 인젝션 규칙에도 안 걸리는 정상 문장에 제로폭만 심는 테스트 4개 추가.
- **프로퍼티 생성기 갭.** `insertZeroWidth`가 위치를 `1 ~ length-1`로 잡아 **경계 삽입을
  원리적으로 생성하지 못했다** — N-1이 프로퍼티를 통과한 이유다. 범위를 `0 ~ length`로 넓히고
  시크릿 바깥에 이웃 문자를 붙이는 `glueNeighbour` 생성기를 추가했으며,
  비가시 문자 집합을 10종(제로폭 5 + soft hyphen + CGJ + VS + U+2800 + 결합 악센트)으로 넓혔다.

**수정마다 뮤테이션으로 잠금을 확인했다** — 각 수정을 되돌리면 대응 테스트가 죽는다:
N-1 되돌림 5 failed, N-2/N-4 좁은 집합 복원 4 failed, N-3 공백 배제 복원 2 failed,
제로폭 임계값 무력화 2 failed, 규칙 삭제 2 failed. 프로퍼티 단독 실행에서도 N-1 되돌림에 3 failed.

### 남은 것
- **F-13 무앵커 41자 base64 런은 미마스킹.** `{40}` 정확 일치라 41자는 통과한다.
  AWS 시크릿은 정확히 40자이므로 설계상 방어 가능하나 F-5/F-10과 같은 축이다.
- **F-11 `applyMasking` 겹침 해소가 세그먼트 수에 대해 이차.** 실측 100KB 12ms →
  200KB 139ms → 400KB 539ms. 100KB 이하에서는 무해하나 상한 없는 입력에는 취약하다.
- **F-14 원문 패스가 추가돼 규칙을 두 번 돌린다.** 최악 실측 41ms(CJK 100KB)라 여유는 있지만
  입력 크기 상한이 없으면 F-11과 함께 문제가 된다. T-007에서 본문 길이 상한을 둘 것.

### 3차 재검증에서 나온 것 — 수정 완료 (4차 패스)
검증자가 BLOCKED 대신 `invisible.ts` 한정 패스를 권고했고 그 판단을 따랐다.
근거: 매 라운드 지적받은 것은 전부 고쳐졌고 잠금까지 증명됐으며, 남은 것은 새 설계 판단이
필요 없는 기계적 수정이었다. **다만 재시도 한도(3회)를 넘겼다는 사실은 그대로 기록한다.**

- **N-6 `\p{Me}` 미커버 — 내 N-4 수정이 만든 구멍.** 유니코드 결합 표시는 `Mn`·`Mc`·`Me`
  세 범주인데 `Mn`만 지웠다. `Me`(U+20E0, U+0488, U+A670)는 NFKD도 건드리지 않아
  `AKIA`+U+20E0+`IOSFODNN7EXAMPLE`이 **플래그도 마스킹도 없이 전문 통과**했다.
  → `\p{M}`으로 3범주를 덮었다. `Mc`가 포함돼 데바나가리 모음기호 등이 프로브에서 사라지지만
  프로브는 매칭 전용 사본이고 규칙 문자 클래스가 전부 ASCII라 오탐 위험이 없다(다국어 산문 3종 회귀 테스트).
- **N-7 C0/C1 제어문자.** `normalizeWithMap`이 성능을 위해 `codePoint < 0x80`을 지름길로
  통과시켜 **프로브와 원문 양쪽에 제어문자가 남아 두 패스를 동시에 깼다.**
  → 지름길을 인쇄 가능 ASCII(0x20~0x7E)로 좁히고 제어문자 판정을 추가했다.
  `\t`·`\n`·`\r`은 남긴다 — mongo 규칙이 줄 경계를 쓰므로 지우면 그 경계가 무너진다.
  `no-control-regex` lint를 우회하지 않으려고 정규식 대신 코드포인트 판정으로 썼다.
- **F-15 `mongodb://` 과매치 — 내 N-3 수정이 만든 오탐.** userinfo에 공백을 허용한 대가로
  `mongodb://localhost:27017 에서 실패, @team 에 공유` 같은 정상 문장이 128자까지 삼켜져
  **모듈이 보존을 약속한 호스트가 지워졌다.** → `@` 뒤가 호스트처럼 보일 때만 매치하는
  룩어헤드(`[A-Za-z0-9._-]{0,64}[.:/]`)를 붙였다. 호스트에는 `.`·`:`·`/`가 오지만
  `@mention`에는 오지 않는다는 점이 두 경우를 가른다. N-3 케이스는 그대로 마스킹된다.

뮤테이션 잠금 확인: `\p{M}`→`\p{Mn}` 3 failed, 제어문자 판정 제거 5 failed,
호스트 룩어헤드 제거 2 failed, ASCII 지름길 복원 3 failed.

### 남은 것 (반려 사유 아님)
- **F-16 `mergeSourceEdits`의 확장 분기가 한 번도 실행되지 않는다.** 유닛·공격·오탐 코퍼스
  127종에서 발화 0회이고 경계 뮤턴트가 전부 생존한다. 두 좌표계의 매치가 같은 시작점에서
  포함 관계로만 겹치기 때문으로 보인다. 부분 겹침 입력을 못 찾았다는 것이지 불가능 증명은
  아니라 값싼 방어를 남기되, **커버리지 부재를 코드 주석에 명시**했다. 지우거나 테스트를
  붙이는 결정은 후속 과제.
- **F-17 프로퍼티 생성기의 비가시 문자 집합이 구현에서 역산돼 있다.** 코드가 이미 처리하는
  문자만 생성하므로 형제 문자(`\p{Me}`, C0)를 원리적으로 만들지 못한다 —
  N-6·N-7이 프로퍼티를 통과한 이유다. 유니코드 속성에서 **직접 표집**하는 생성기가 필요하다.
  이 구조적 갭이 T-004에서 세 번 반복됐다(2차 filter 미러링 → 3차 경계 미생성 → 4차 집합 역산).
- **F-13** 무앵커 41자, **F-11/F-14** 시크릿 밀집 입력의 이차 곡선(400KB 1.7초).
  T-007에서 **본문 길이 상한을 반드시 둘 것** — 상한 없이 넘기면 저장 API가 통째로 멈춘다.
- **FP-2** `api_key=<your key>` 꺾쇠 안 공백으로 `<your`가 마스킹된다(보수적 방향, 경미).

**F-17 해소 (4차 패스).** 프로퍼티 생성기가 하드코딩 목록 대신 **유니코드 속성에서 직접 표집**한다.
`\p{M} | \p{Default_Ignorable_Code_Point} | C0/C1 제어문자`를 BMP 전역에서 훑어 178자를 뽑는다
(`\t`·`\n`·`\r`은 제외 — 지워지지 않는 것이 정상이다).
코드가 무엇을 지우는지와 **무관하게** 표집하므로 다음번에 또 어떤 범주를 빠뜨리면 생성기가 먼저 잡는다.
효과 확인: `\p{M}`→`\p{Mn}` 되돌림에 프로퍼티 4 failed, 제어문자 판정 제거에 3 failed —
**하드코딩 목록이었으면 둘 다 통과했을 것이다.**

### 4차 검증에서 나온 것 — 미해결 (BLOCKED 사유)
- **N-8 (회귀) 점 없는 호스트에서 비밀번호 유출.** F-15 오탐을 막으려 넣은 호스트 룩어헤드가
  compose 서비스명(`@mongo`, `@db`)·`@localhost`를 호스트로 인정하지 않아 **3차에 막던 것을 흘렸다.**
  룩어헤드 변형 3종 실측: 룩어헤드 없음 → 미탐 0/5·오탐 2/2, 룩어헤드 있음 → 미탐 4/5·오탐 0/2.
  **호스트 쪽 조건으로는 둘 중 하나만 고를 수 있다.** 근본 원인은 N-3이 넓힌 비밀번호 문자 클래스
  `[^/@\n]{1,128}`가 산문을 "비밀번호"로 삼켜 뒤의 `@mention`이 호스트 자리에 오는 것이다.
  → 현재는 룩어헤드를 빼 **유출 0** 상태로 두고 오탐을 감수한다. 근본 해결은 URI 구조 파싱.
- **N-9 `\p{Cf}` 29종 미커버.** 6,548 코드포인트 스윕에서 `Cf`이면서 `Default_Ignorable`이 아닌
  29종(U+0600–0605, U+06DD, U+070F, U+0890, U+0891, U+08E2, U+110BD, U+110CD, U+13430–1343F)이
  **플래그도 마스킹도 없이 통과**한다. `\p{Cf}`로 걷어내면 시크릿이 완전 복원된다.
  N-6과 완전히 같은 축이다 — `isControl()`이 이 중 U+FFF9–FFFB 3개만 하드코딩으로 알고 있다.
- **F-17 미해소.** 생성기의 표집 조건
  (`\p{M} | \p{Default_Ignorable_Code_Point}` + C0/C1)이 `invisible.ts` 구현 집합과 **동일**하다.
  하드코딩 목록이 유니코드 속성 표현으로 바뀌었을 뿐 여전히 구현에서 역산돼 있고,
  실제로 U+2800도 U+0600도 생성하지 못해 **N-9가 프로퍼티를 그대로 통과했다.**
  "다음번에 또 어떤 범주를 빠뜨리면 생성기가 먼저 잡는다"는 선언이 바로 이번에 실패했다.
- **FP-3 (신규, 경미)** ZWJ 이모지 시퀀스(`👨‍👩‍👧‍👦`)의 U+200D가 제로폭 계수에 잡혀
  4개 초과 시 `injection-suspect`. F-9가 U+FE0F는 제외했으나 ZWJ는 남겼다. 마스킹 아님(플래그만).
- **F-11/F-14 갱신.** 새 최악은 `Bearer ` 런 — 100KB 241ms / 200KB 897ms / **400KB 3187ms**.
  `Bearer Bearer Bearer…`가 매 7바이트마다 세그먼트를 만든다. **T-007의 본문 길이 상한은 선택이 아니다.**

### 5차 패스 — 결정 1~4 구현 결과

**결정 1 (URI 구조 파싱).** `MONGO_URI_RE`를 버리고 스킴 → authority → 마지막 `@` → 첫 `:`
순서로 파싱한다. 핵심은 **공백을 authority 종료로 보는 것**이다 — `27017` 뒤 공백에서
authority가 끝나므로 뒤의 `@team`은 경계 후보조차 되지 않는다(F-15가 구조적으로 닫힌다).
`@`가 authority 안에 있으면 호스트 모양을 따지지 않으므로 compose 서비스명도 마스킹된다(N-8 종결).
- **관대 모드**를 한 겹 뒀다. 엄격 해석으로 `@`를 못 찾았을 때만 공백을 건너뛰어 다시 본다
  (`<db user name>:pw@host`·`my user:pw@host` — N-3 케이스는 URI로는 불법이지만 실제 기록에 흔하다).
  산문 오인을 막는 조건은 **`:`가 있고 비밀번호 쪽에 공백이 없을 것**. 정상 문장은 비밀번호
  자리에 산문이 통째로 들어와 공백을 포함하므로 여기서 걸러진다. 이 가드를 지우면 F-15가 재발한다(실측 2 failed).
- 부수 효과: mongo 정규식의 백트래킹이 사라져 `Bearer ` 런 64KB가 190ms → 57ms가 됐다.

**결정 2 (`\p{Cf}`·`\p{Cc}` 확대).** `isControl()`의 하드코딩 열거를 `\p{Cc}`로 대체하고
`\t`·`\n`·`\r`만 `isIgnorable`에서 되살렸다. U+FFF9–FFFB 하드코딩은 `\p{Cf}`에 흡수됐다.
인젝션 "과도한 제로폭" 계수(`ZERO_WIDTH_RE`)는 **넓히지 않았다** — F-9의 U+FE0F 근거 그대로.

**결정 3 (생성기 독립).** 표본을 두 통으로 나눈다. 기대값을 가르는 기준은 구현이 아니라 **렌더링**이다:
- `Cc`·`Cf`·`Cs`·`Mn`·`Mc`·`Me`·`Default_Ignorable` → 폭도 글리프도 없다 → **마스킹 필수**
- `Co`·`Zs`·`Zl`·`Zp`와 그 밖의 문자 → 시크릿을 눈에 보이게 끊는다 → 마스킹을 요구하지 않고,
  대신 **바깥에 붙어도 마스킹이 깨지지 않을 것**을 요구한다(가시 문자판 N-1)
범주 열거(범주당 64자 균등 표집) + 전 평면 무작위 표집 600점. `invisible.ts`를 import하지 않는다.
효과 확인: `\p{Cf}` 확대를 되돌리면 **프로퍼티 3개가 죽는다.** 같은 뮤턴트에 구 생성기는
22개 전부 통과했다 — F-17이 "선언"이 아니라 실측으로 닫혔다.

**결정 4 (길이 상한).** `SANITIZE_MAX_INPUT_CHARS`(기본 65536, `.env.example` 포함).
초과 시 `SanitizeInputTooLargeError`(code `SANITIZE_INPUT_TOO_LARGE`, 실제 길이와 상한 포함)를
던진다. 자르지 않는다 — 조용한 절단은 "검사되지 않은 시크릿을 호출자가 모르고 저장하는" 경로다.
양의 정수가 아닌 env 값은 기본값으로 되돌린다(오설정이 게이트를 무력화하지 못하게).

### 남은 것 (5차 이후)

- **F-11 갱신.** `collectEdits`의 이차 곡선은 **그대로 남아 있다.** 결정 4가 알고리즘 대신
  상한으로 막기로 한 것이므로 의도적이다. 상한 안에서 최악 57ms이고, 이차 구조상
  `SANITIZE_MAX_INPUT_CHARS`를 크게 올리면 다시 초 단위로 튄다. **env를 올릴 때는 재측정할 것.**
  (선형화 패치를 시험해 봤으나 64KB에서 57ms → 35ms로 이득이 작고 어떤 테스트도 잠그지 못해
  결정 범위 밖 변경으로 판단해 되돌렸다.)
- **F-18 (신규) `Co`·`Zs`는 프로브에서 지우지 않는다.** NBSP·EM SPACE·사설 영역 글리프를
  시크릿 한가운데 끼우면 마스킹되지 않는다. 일반 공백과 같은 취급이며 **사람 눈에도 끊겨 보이므로**
  의도된 선택이다. 다만 NBSP는 웹 복사로 자연히 섞이는 문자라 "보인다"는 전제가 약한 편이다 —
  프로브에서 `Zs`를 지우면 40자 base64 런이 공백으로 나뉜 산문에서 합쳐질 위험이 새로 생기므로
  코퍼스 없이 결정하지 않는다. T-007 이전 판단 대상.
- **F-19 (신규) mongo 관대 모드는 `:` 없는 형태를 포기한다.** `mongodb://my user@host`처럼
  비밀번호가 없고 사용자명에만 공백이 있으면 마스킹하지 않는다. 자격증명이 아닌 산문과
  구별할 근거가 없어서다(사용자명 단독은 비밀번호보다 민감도가 낮다).
- **F-13**(무앵커 41자), **F-5·F-10**(`ghp_`/JWT/postgres·`*_TOKEN=` 앵커), **F-16**(`mergeSourceEdits`
  확장 분기 커버리지 0), **FP-2**(`api_key=<your key>`), **FP-3**(ZWJ 이모지 계수) 그대로 남아 있다.
- **F-1/F-3**(마스킹 종류·규칙 id가 `sanitize()`에서 사라짐)은 T-007에서 결정할 항목으로 유지.

### 인간 비준이 필요한 스펙 수정 (5차, G5 지적)
길이 상한이 **어느 계약 문서에도 없다.** core에만 존재하는 상태라 계층이 어긋나 있다.

- **S-A `specs/04-api.md`에 본문 길이 상한을 명시할 것.** 기본 65536자, 초과 시 응답 코드
  (**400 vs 413** — 오버사이즈 페이로드의 관용 코드는 413이다), 에러 코드명.
  그리고 **상한이 요청 단위인지 필드 단위인지**를 함께 규정할 것 —
  현재는 `sanitize()` 호출 단위라 섹션별로 부르면 5섹션 × 65536 = 327KB가 게이트를 통과한다.
- **S-B `packages/contracts/src/record.ts`의 섹션 필드에 `.max()`를 둘지 결정할 것.**
  현재 `min(10)`만 있다. CLAUDE.md는 "API 계약은 contracts Zod 스키마가 단일 소스"라 하는데
  입력 길이 제약이 core에만 있는 것은 계층 불일치다.
  둔다면 **계약 변경이므로 G3(인간 승인)**, 두지 않는다면 "입력 길이 게이트는 core가 소유한다"는
  예외를 명시해야 한다. **T-004에는 이 결정 권한이 없다.**
- **S-C `specs/02` 31행** — F-7 계류 중: `sanitizeFlags: string[]`를
  "2종 고정 + 추가 시 마이그레이션 동반"으로 명확화.

### 6차 패스 — N-10 (5차 결정 1이 만든 구멍) 종결

**증상.** 5차 검증이 mongo 자격증명 미탐 7종으로 RED. 그중 5종은 4차(정규식) 대비 **신규 회귀**다.
`sanitize("mongodb://appuser:Str0ngPass @cluster0.example.net/db")`가 입력을 그대로,
**플래그도 없이** 돌려줬다 — 평문 비밀번호가 레코드·청크·임베딩·LLM 컨텍스트로 넘어간다.

**근본 원인 — 파싱 "순서".** 결정 1은 경계 정의를 옳게 잡았지만 순서를 틀렸다.
"authority 끝을 먼저 정하고 그 안에서 마지막 `@`를 찾는다"는 순서는 authority 종료 문자
(`/`·`?`·공백류)가 **비밀번호 안에** 들어 있으면 그 지점에서 authority를 끊어 `@`를 못 찾는다.
즉 **경계 판정이 비밀번호 내용에 의존**했다. 종료 문자 대역 전체가 미탐 대역이었고,
5차가 F-15를 막으려 "공백을 authority 종료로 본다"를 핵심 방어로 삼은 것이 그 대역을 넓혔다.

**수정 — 순서를 뒤집는다.** `@` 후보를 먼저 고르고 **뒤가 호스트 모양인지**로 검증한다.
비밀번호에 무엇이 들어 있든 `@` 뒤의 호스트는 여전히 호스트 모양이므로 판정 근거가 옮겨간다.

1. 스킴(`mongodb://`·`mongodb+srv://`) 뒤부터 **줄 끝까지**(개행 전, 상한 512자) 훑는다.
2. 그 구간의 `@`를 **뒤에서부터** 보며 뒤가 `[A-Za-z0-9._-]{1,255}(:\d{1,5})?` 또는
   `\[IPv6\](:\d{1,5})?` 뒤에 `/`·`?`·`#`·공백류·줄끝이 오는지 검사한다.
3. 통과한 `@`에 대해 **userinfo 정당성**을 따진다. 실패하면 다음 `@`로 물러난다.
   - **엄격**: RFC 3986 userinfo 문자집합 + 실무 예외 `?`·`/`·`@`.
     (`?`·`/`는 RFC userinfo에 **없지만** 이스케이프 없이 들어오는 것이 현실이고 그게 N-10의 핵심 케이스다.
      `@`는 `svc:P@ssw0rdLong@host` 때문이다.) `:` 없는 형태(`mongodb://svcuser@host`)도 여기서 인정된다.
   - **관대**: `:`가 반드시 있고, 비밀번호는 **후행 공백만 트림한 뒤 내부 공백이 없어야** 한다.
4. userinfo를 첫 `:`로 가르고 user·pass를 각각 판정한다(5차와 동일).

**userinfo 정당성 검사가 F-15 오탐을 막는 유일한 방어선이다.** 2번만으로는
`mongodb://localhost:27017 에서 문제 발생, @team 에 공유했다.`의 `@team`이 호스트 모양을
통과해 호스트가 지워진다. 비밀번호 자리의 **내부** 공백이 산문과 자격증명을 가른다.

**7종 처리 결과** (전부 `mongodb://appuser:<PW>@cluster0.example.net/db`):

| 비밀번호 | 4차(정규식) | 5차 | 6차 |
|---|---|---|---|
| `Str0ngPass?x` | 마스킹 | LEAK | **마스킹** |
| `Str0ngPass ` (후행 공백) | 마스킹 | LEAK | **마스킹** |
| `Str0ngPass` + 탭 | 마스킹 | LEAK | **마스킹** |
| `Str0ngPass` + NBSP | 마스킹 | LEAK | **마스킹** |
| `Str0ngPass` + CR | 마스킹 | LEAK | **마스킹** |
| `Str0ngPass/x` | 누출 | LEAK | **마스킹** |
| `Str0ngPass` + LF | 누출 | LEAK | **명시적 포기** (아래 F-20) |

**대역 스윕 테스트가 이번 수정의 핵심 산출물이다.** authority 종료 후보 문자 21종
(ASCII 구조 문자 3 + ASCII 공백류 4 + 유니코드 공백류 8 + RFC 밖 기호 6)을 표로 고정하고
각각을 **비밀번호 중간·끝** 두 자리에 넣어 42 케이스를 `it.each`로 단언한다.
기대는 `mask`(완전 일치) 또는 `abandon`(원문 그대로 — 부분 마스킹도 호스트 삭제도 아님) 둘뿐이고
**침묵이 없다.** 다섯 라운드 내내 "지적받은 케이스 3개만 고쳐 옆칸이 열리는" 패턴이 반복된
자리라, 대역이 움직이면 테스트가 먼저 울게 만드는 것이 목적이다.

### 6차에서 새로 명시하는 포기·한계

- **F-20 (신규) 줄을 넘는 URI를 포기한다.** `mongodb://user:pw\n@host`는 산문과 구별할
  구조적 근거가 없다 — 개행 하나를 허용하면 문단 전체가 userinfo 후보가 된다. F-19와 같은 취급.
  `\r`는 개행으로 보지 않고 공백류로 다루므로 **후행 CR은 마스킹된다.**
- **F-21 (신규) 비밀번호 "중간"의 공백류를 포기한다.** 관대 갈래가 요구하는
  "비밀번호에 내부 공백 없음"이 F-15를 막는 유일한 방어선이라 풀 수 없다.
  후행 공백은 트림 후 판정하므로 **끝**에 오면 마스킹된다. 스윕 표에 11종 전부 고정돼 있다.
- **F-22 (신규) userinfo 스캔 상한 512자.** 스킴 매치마다 줄 끝까지 훑으면 매치 수 × 줄 길이로
  이차가 된다(F-11과 같은 축). 상한 밖 자격증명은 포기하며 그 포기도 테스트로 고정했다
  (400자 사용자명 → 마스킹, 600자 → 포기). **`SANITIZE_MAX_INPUT_CHARS`와 달리 이건 env가 아니다** —
  임계값이 아니라 형태 규격이고, 오설정이 게이트를 무력화하는 경로를 만들지 않는다(specs/03 §6 판정과 동일).
- **F-23 (신규, 오탐) `@`가 공백 없이 URI에 붙으면 호스트를 삼킬 수 있다.**
  `mongodb://localhost:27017/db@team`은 엄격 갈래가 `localhost:27017/db`를 userinfo로 인정해
  호스트가 지워진다. 같은 축으로 `mongodb://u:p@host/db?owner=ops@example.com`은
  역방향 스캔이 이메일 도메인을 호스트로 집는다. 둘 다 **URI와 멘션/이메일 사이에 공백이 0인**
  형태이고 F-15 코퍼스가 보여 준 실제 표기(항상 공백이 있다)와 어긋난다.
  위험 비대칭(미탐 > 오탐)에 따라 감수한다. **5차 대비 새로 생긴 오탐 축이므로 명시해 둔다.**

### 6차 콜드 성능 (64KB 상한, 프로세스마다 첫 호출 1회)

| 입력 모양 | 5차 | 6차 |
|---|---|---|
| `Bearer ` 런 | 174ms | 181ms |
| `mongodb://` 런 | 11ms | 183ms |
| `mongodb://x@a ` 런 (**새 최악**) | 9ms | **231ms** |
| `mongodb://a:b@c/` 런 | 154ms | 69ms |
| `a@b ` 한 줄 | 12ms | 9ms |
| `@` 밀집 한 줄 | 9ms | 9ms |
| CJK 산문 | 54ms | 50ms |
| `mongodb://localhost:27017 에서 실패, @team …` 반복 | 87ms(오탐) | 24ms(정상) |

**이전 보고의 57ms는 워밍업 후 수치였다.** 같은 입력의 콜드는 174~181ms이고 워밍업 후 90~100ms로
내려간다. 새 최악 231ms는 목표 500ms 대비 2.2배 여유다.
5차 대비 느려진 두 행은 **일을 안 하다가 하게 됐기 때문**이다 — `mongodb://x@a ` 런에서
5차는 자격증명을 하나도 못 찾았고(그게 N-10이다) 6차는 4,681건을 찾는다. 비용은 파싱이 아니라
`collectEdits`의 이차 곡선(F-11)이 세그먼트 4,681개 위에서 도는 데서 나온다.
`STRICT_USERINFO_RE`를 charCode 룩업 테이블로 바꾸면 `mongodb://` 런이 183→121ms가 되지만
최악 행은 개선되지 않고 어떤 테스트도 잠그지 못해 **되돌렸다**(5차의 선형화 패치와 같은 판정).
**`SANITIZE_MAX_INPUT_CHARS`를 올릴 때는 반드시 재측정할 것.**

### 7차 패스 — N-11과 **구조적 원인** 해소

6차 검증이 RED를 냈고 **구조적 진단**을 함께 내놨다. 여섯 라운드가 전부 같은 모양이었다:

```
F-8(비가시 문자 열거) → N-3(userinfo 문자 클래스) → F-15/N-8(호스트 룩어헤드 클래스)
→ N-10(authority 종료 문자 집합) → N-11(호스트 경계 집합 + 호스트 모양 규격)
```
매번 **어떤 열거가 판정하느냐**만 바뀌었고, **"열거에 없는 문자 = 조용한 평문 통과"라는 성질은
한 번도 제거되지 않았다.** 같은 레포의 `invisible.ts`는 이 문제를 이미 풀었다 —
개별 문자 열거를 버리고 유니코드 **범주**로 가면서 "범주 단위로만 넓힌다"를 규칙으로 못박았다
(F-8→N-2→N-6→N-9를 겪고서). **mongo 규칙만 그 원칙을 채택하지 않았다.**

**N-11 실측 유출** — 이 레포의 기록은 마크다운이고 산문은 한국어인데, 가장 흔한 표기가 전부 샜다:
마크다운 백틱·링크·괄호, 문장 끝 쉼표, **한국어 마침표(`。`)**, 세미콜론, YAML 인용,
**레플리카셋 시드 리스트(RFC 합법 MongoDB 표준 문법, Atlas 기본 형태)**, compose의 `$PORT` 보간,
빈 포트, 6자리 포트, 255자 초과 호스트, IDN 호스트, 와일드카드.
ASCII 인쇄 가능 94자 중 **25자**가 호스트 뒤에 오면 유출이었다. 4차·5차 대비 **신규 회귀**다.

**해소: 호스트 모양 검증을 통째로 걷어냈다.**
핵심 통찰은 **그 검증이 애초에 불필요했다**는 것이다. F-15(정상 산문의 호스트 삭제) 방어는
**userinfo 정당성 검사만으로 성립한다** — strict 런은 공백에서 끊기고 lenient는 비밀번호
내부 공백을 배제하므로, `mongodb://localhost:27017 에서 실패, @team`은 두 갈래 모두에서 탈락한다.
호스트 검증은 덧붙인 열거였을 뿐이고, N-11 대역 전체가 거기 살았다.

남긴 조건은 하나뿐이고 **열거가 아니라 구조적 최소**다: `@`가 스팬 맨 끝이면 뒤에 호스트가
존재할 수 없으므로 경계가 아니다(`...?appName=svc@`). 위치 판정이라 형제 문자를 놓치는 성질이 없다.

**테스트 축도 바꿨다.** 기존 대역 스윕 표는 "비밀번호 **안**의 종료 후보 문자"만 훑어
N-11이 산 자리(호스트 **뒤**)를 비껴갔다. 새 블록은 열거가 아니라 **외부 기준**으로 잠근다 —
**ASCII 인쇄 가능 94자 전수** + 실제 기록 형태 8종 + 호스트 모양 5종.

검증: N-11 15종 유출 **0**, F-15 오탐 0, N-8/N-10 회귀 유지, 유닛 310 그린.
뮤테이션 — **옛 호스트 모양 검증을 되살리면 39개가 죽는다**, 꼬리 `@` 구조 조건 제거 시 3개가 죽는다.

- **F-23** `mongodb://localhost:27017/db@team`(공백 0) 과마스킹 — 기존, 오탐에 그친다.
- **F-25 (구조) 프로퍼티 생성기가 이 축을 원리적으로 못 만든다.**
  `sanitize.property.spec.ts`가 호스트를 상수(`cluster0.ab12c.mongodb.net`)로 고정하고
  user/pass만 생성한다. **F-17("생성기가 구현에서 역산됨")의 네 번째 반복**이다.
  비가시 문자 축에서는 범주 표집으로 풀었지만 mongo 축은 아직 대역 스윕 표로만 막았다.
  호스트·포트·URI 뒤 문자를 생성하지 않는 한 다음 라운드도 프로퍼티를 그대로 통과한다.
- **F-20/F-21** LF·비밀번호 중간 공백류 포기는 유지. **F-11** 이차 곡선 유지(상한 올릴 때 재측정).

### 8차 패스 — N-12: 열거가 **판정자만 바꿔** 재발했다

7차 검증이 다시 RED를 냈다. 호스트 쪽 열거를 제거하자 **그 열거가 가려 주던 `STRICT_USERINFO_RE`의
결함이 노출**됐다. 판정자만 `HOST_AFTER_AT_RE` → `STRICT_USERINFO_RE`로 옮겨간 것이다.

**메커니즘.** strict 갈래는 허용 문자 런 안의 마지막 `@`를 찾으면 **즉시 반환**한다(lenient 미실행).
런은 집합 밖 문자에서 끊긴다. 그래서 **비밀번호에 `@`가 있고 그 뒤에 집합 밖 문자**
(`"#<>[\]^\`{|}` 12자 + 모든 비-ASCII)가 오면 런이 진짜 경계 앞에서 잘려
**비밀번호 내부의 `@`가 경계로 뽑히고 나머지가 평문으로 남았다.** 실측 41종.

악질적인 점: **`flags=["secret-masked"]`가 붙는다.** 기록은 "새니타이즈됨"으로 보이는데
비밀번호가 들어 있다. `P@ssw0rd` 류 비밀번호와 `#[{|^` 특수문자는 강한 비밀번호의 표준 조합이고,
Atlas의 이메일형 사용자명(`ops@corp.com`)만으로도 성립한다.

**해소 ① `@`를 strict 집합에서 뺐다.** 그러면 런이 `@`에서 끊겨 strict가 실패하고,
lenient가 올바른 마지막 `@`를 찾는다. 검증자가 이 수정을 미리 실측했다(유출 46→8).

**해소 ② 과마스킹 → 유출 전환을 닫았다.** `collectEdits`가 부분 겹침 세그먼트를 확장이 아니라
**폐기**해서, mongo 규칙이 뒤 규칙의 시크릿을 앞부분만 덮으면 그 규칙 세그먼트가 통째로 버려지고
**꼬리가 평문으로 남았다**(`?api_key=tok@S3cr3tV4lu3XYZ` → 값 꼬리 유출,
`maskEmail:true`에서 이메일 부분 유출). 겹치면 확장하도록 고쳤다.
**이로써 F-24는 오탐이 아니라 유출이었음이 확인됐고 함께 닫혔다.**

**해소 ③ 테스트 축을 또 바꿨다.** 같은 실패가 **세 번** 반복됐다 — 표는 매번 한 칸 옆을 훑었다:
6차 표는 비밀번호 안 종료 문자(기저 비번에 **`@`가 없었다**), 7차 표는 호스트 **뒤** 문자,
실제로 열린 자리는 비밀번호 안 **`@` 뒤** 문자.
새 블록의 기저 비밀번호는 **반드시 `@`를 포함한다.**

검증: N-12 58종 유출 **0**, 과마스킹 전환 2종 닫힘, 누적 회귀(N-3·N-8·N-10·N-11·F-15) 전부 유지,
유닛 354 그린. 뮤테이션 — **`@`를 strict 집합에 되돌리면 40개**, 겹침 폐기를 복원하면 2개가 죽는다.

### 남은 것 (8차 이후)
- **F-26 (신규) 줄 끝 `@`는 무플래그로 통과한다.** `MONGO_URL=mongodb://svcuser:PW@` (로그 절단 등)는
  `hasHostAfter`의 의도된 동작이지만 **평문 비밀번호가 플래그도 없이 남는다.**
  뒤에 호스트가 없으니 "자격증명이 아니다"로 볼 수도, "잘린 URI"로 볼 수도 있다. 판단 필요.
- **F-25 유지 — 프로퍼티 생성기가 mongo 축을 원리적으로 못 만든다.**
  호스트를 상수로 고정하고 user/pass만 생성한다. **F-17의 네 번째 반복**이고,
  N-11·N-12가 프로퍼티를 그대로 통과한 이유다. 비가시 문자 축은 범주 표집으로 풀었지만
  mongo 축은 아직 대역 스윕 표로만 막았다. **다음 라운드가 이 축을 볼 때 프로퍼티에 의존하면 안 된다.**
- **F-20/F-21/F-22** 명시적 포기 유지. **F-11** 이차 곡선 유지.
- 성능 주석의 "최악 58ms"가 실측 178ms와 3배 벌어져 있다(수치만 낡음).


### 8차 검증 중단 시점의 미해결 (인간 결정으로 라운드 종료)
- **N-13 (미수정) `:` 없는 userinfo가 샌다.** `mongodb://tokenonly@host` 형태.
  lenient 갈래가 `:`를 필수로 요구하고(F-19), `@`를 strict 집합에서 뺐으므로(N-12 수정)
  **strict 갈래는 이제 `@`를 절대 찾지 못한다.** 둘이 겹쳐 이 형태가 어느 갈래에도 안 걸린다.
  F-19는 "사용자명 단독은 민감도가 낮다"를 근거로 포기했으나, **토큰을 사용자명 자리에 넣는
  형태**(`mongodb://<apikey>@host`)는 민감도가 낮지 않다.
- **8차 검증은 완주하지 못했다.** 위 발견 직후 인간 결정으로 정지했으므로,
  N-12 수정의 전수 검증(누적 회귀·뮤테이션·성능)은 미완이다.
  다만 오케스트레이터의 직접 실측으로 N-12 58종 유출 0, 누적 회귀 유지, 유닛 354 그린은 확인됐다.
