# 08 — 퍼블리싱 파이프라인 (자동 아티클 생성)

축적된 레코드가 임계치를 넘으면 **사람이 읽는 글**(블로그·게시판 형태)로 자동 편찬한다.
지식 보관소는 에이전트용 검색 인터페이스지만, 아티클은 팀·외부 독자용 출판물이다.

## 0. 설계 철학 — "AI 티"는 문체 문제가 아니라 밀도 문제다

AI 냄새가 나는 글의 공통점은 문체가 아니라 **내용 없음**이다: 구체적 숫자·에러 원문·타임스탬프
없이 일반론이 대칭 구조로 반복되는 것. 따라서 대응의 우선순위는:

1. **팩트는 코드가, 서사는 모델이** — 통계·타임라인·차트 데이터는 결정론적 코드가 DB에서 계산한다.
   LLM은 이미 계산된 팩트를 받아 서사만 쓴다. 숫자를 지어낼 경로 자체를 없앤다.
2. **실데이터 밀도 강제** — 에러 원문 인용, 실제 날짜, 실제 명령어가 임계 개수 미만이면 초안을 반려한다.
3. **문체 린터** — AI 상투 패턴을 규칙으로 걸러낸다 (§4).
4. **스타일 주입** — 작성자가 쓴 실제 글 2~3편을 few-shot으로 넣어 개인 문체를 이식한다.
5. **전자동 발행 금지** — draft까지만 자동. 발행은 사람이 한다. 이 마지막 10%의 사람 편집이
   "AI 티 제거"의 최종 방어선이며, 편집 diff는 다시 스타일 개선 데이터가 된다.

## 1. 아티클 유형과 트리거

| 유형 | 트리거 (worker가 야간 배치로 판정) | 내용 |
|---|---|---|
| A. 케이스 스터디 | 단건 레코드가 (피드백 helped >= 2) 또는 (조회 >= N) | 한 사건의 서사: 증상 → 추적 → 원인 → 해결 → 교훈 |
| B. 패턴 아티클 | 동일 태그·유사 클러스터 레코드 >= 3건 | "우리는 왜 자꾸 X에서 넘어지는가" — 반복 원인 분석 |
| C. 이격 리포트 | divergence가 모델·도구 기준 >= 3건 | "이 모델이 자주 틀리는 것들" — context/correction 집계 |
| D. 주간 다이제스트 | 매주 1회, 신규 레코드 >= 5건일 때만 | 신규 기록 요약 + 통계 + 검색 적중 사례 |

트리거 판정은 `articles` 후보 큐에 적재만 한다. 생성 실행은 사람이 후보 목록에서 골라 개시하거나
`--auto` 플래그로 배치 실행한다 (비용 통제).

## 2. 데이터 모델

```ts
// articles
{ _id, kind: "case"|"pattern"|"divergence-report"|"digest",
  sourceRecordIds: ObjectId[],
  title, slug,
  facts: object,          // §3에서 코드가 계산한 팩트 팩. LLM 산출물 아님
  body: string,           // Markdown (mermaid 블록 포함)
  charts: ChartSpec[],    // §5. 데이터+타입 선언, 렌더는 프론트
  lintReport: object,     // §4 결과
  status: "candidate"|"draft"|"published"|"rejected",
  editHistory: {at, diffSummary}[],   // 사람 편집 기록 — 스타일 개선 데이터
  createdAt, publishedAt }
```

## 3. 팩트 추출기 (결정론, LLM 미사용)

소스 레코드들로부터 코드가 계산한다:
- 기간·건수·태그 분포, 심각도 분포, 프로젝트 분포
- 타임라인: 레코드 createdAt + incident timeline 필드 병합
- 반복 지표: 동일 클러스터 내 최초~최근 간격, 재발 횟수
- divergence 집계: 모델별·도구별 빈도, correction 유형 분류
- 인용 후보: 에러 원문·명령어 스니펫 (원문 그대로, flags 확인 후)

이 출력(`facts`)이 LLM 프롬프트에 주입되고, **본문에 등장하는 모든 수치는 facts에 존재해야 한다** —
인용 검증과 같은 방식으로 후처리 대조하며, facts에 없는 숫자는 반려 사유다.

## 4. 문체 파이프라인

```
아웃라인 생성 → 초안 생성(facts + 스타일 few-shot 주입) → 문체 린트 → (위반 시 지적사항 포함 재작성, 최대 2회)
→ 팩트 대조 → 다이어그램 컴파일 검증(§5) → draft 저장 → [사람 편집·발행]
```

### 문체 린트 규칙 (자동, 규칙 기반)
- 금지 표현: "결론적으로", "~라고 할 수 있습니다", "주목할 만한 점은", "혁신적인", "게임체인저",
  "~하는 것이 중요합니다", 이모지, 과장 수식 연쇄
- 구조 패턴: 3개 항목 대칭 나열이 2회 이상 반복, 모든 문단이 같은 길이(±1문장), 소제목마다 불릿 목록
- 밀도 하한: 본문 1000자당 구체 팩트(수치·날짜·코드·에러 원문) 3개 이상, 코드/로그 블록 1개 이상
- 문장 다양성: 연속 5문장 동일 어미 금지
- 도입부: "이 글에서는 ~를 다룹니다"류 메타 서두 금지 — 사건 한복판에서 시작

### 유형별 서사 템플릿 (구조 로테이션)
같은 유형이라도 템플릿 3종을 로테이션해 구조 획일화를 피한다.
예: 케이스 스터디 = (a) 시간순 수사 서사, (b) 결론 선행 후 역추적, (c) 잘못된 가설 3개를 기각하는 구성.

## 5. 시각화 자동 생성

두 트랙으로 나눈다. **차트(데이터)는 선언으로, 다이어그램(구조)은 코드 생성+컴파일 검증으로.**

### 5.1 차트 — ChartSpec 선언 (LLM이 데이터를 만들지 않음)
팩트 추출기가 `{type: "bar"|"line"|"heatmap"|"timeline", data, caption}` 형태로 산출하고
프론트(web)가 렌더한다. 유형별 기본 차트:
- 패턴 아티클: 태그 빈도 바, 발생 시계열, 재발 간격
- 이격 리포트: 모델×이격유형 히트맵, correction 유형 분포
- 다이제스트: 주간 기록 추이, 프로젝트별 기여

### 5.2 다이어그램 — mermaid 생성 + 검증 루프
원인 연쇄(flowchart), 사건 타임라인(timeline), 상태 흐름 등은 LLM이 mermaid 코드로 생성하되,
**mermaid 파서로 컴파일 검증**하고 실패 시 에러 메시지와 함께 재생성(최대 2회), 재실패 시 해당
다이어그램만 생략한다. 깨진 다이어그램이 실리는 것보다 없는 편이 낫다.

### 5.3 렌더
web에 `/articles` 라우트: Markdown 렌더 + mermaid + 차트 컴포넌트. 발행물은 정적 캐시.
내보내기: 단일 HTML(공유용). PDF는 백로그.

## 6. 품질 평가 (eval:style)
- 린트 통과율 100% (자동)
- 팩트 대조 위반 0건 (자동)
- 블라인드 판정: 사람이 쓴 글 3편과 섞어 LLM-judge에게 "AI 작성 추정" 판별 → **판별 정확도가
  낮을수록 좋음** (목표: 우연 수준 근접). 분기별 사람 블라인드 테스트로 교차 검증
- 발행률: 후보 대비 실제 발행 비율 추적 — 낮으면 파이프라인이 쓰레기를 만들고 있다는 신호

## 7. 경계
- 전자동 발행 금지. 외부 공개는 사람 승인 후에만
- sanitizeFlags 있는 레코드의 원문 인용 금지
- 아티클 생성은 검색·기록 경로와 리소스 격리(야간 배치) — 본 기능이 핵심 경로를 느리게 하면 안 됨
