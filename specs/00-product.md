# 00 — 제품 정의

## 문제
1. 트러블슈팅 지식이 프로젝트별로 파편화되어 재발 시 처음부터 다시 판다.
2. AI 에이전트가 프로젝트마다 같은 이격(환각 API, 잘못된 버전 가정, 스펙 드리프트)을 반복하는데 어디에도 기록되지 않는다.
3. 지식이 사람용 문서로만 있으면 에이전트가 소비하지 못한다. 에이전트가 읽고 쓰는 형태여야 루프가 닫힌다.

## 핵심 루프
```
에러 조우 → search_knowledge → (있음) 해결 절차 적용 / (없음) 직접 해결 → record_knowledge
이격 발견 → record_knowledge(type: divergence) → 다음 프로젝트의 CLAUDE.md·스킬로 환류
```
각 프로젝트 CLAUDE.md에 "디버깅 전 search, 해결 후 record" 한 줄로 연결된다.

### 태스크 자동 완결률의 정의

**이 절이 공식 정의다.** 위 표의 `>= 70%`는 여기서 정의한 값에만 적용되고,
다른 계산식으로 낸 값에는 적용되지 않는다.

- **분자** — `eval/loop-log.jsonl`의 **최종 엔트리**가 GREEN(로그에 섞여 있는 비규약
  동의어 `done` 포함)이면서 `attempts <= 3`인 태스크 수.
  3은 `.claude/skills/task-loop/SKILL.md`가 정한 재시도 한도다.
  **규약이 재시도 3회를 정상 경로로 정의했으므로, 그 안에서 끝난 것은 하네스가 스스로 처리한 것이다.**
- **분모** — `eval/loop-log.jsonl`에 엔트리가 하나라도 있는 태스크 수.
  계측되지 않은 태스크는 분모에 넣지 않는다. 대신 그 사실을 **태스크 계측률**로 따로 싣는다.
- **산출기** — `tools/portfolio-metrics.ts`의 `completion.withinRetryLimit`.
  목표 판정은 같은 모듈의 `meetsTarget` **하나만** 쓴다. 손으로 계산하지 않는다.

같은 로그에서 나오는 다른 두 값은 **자동 완결률이 아니다.** 지우지 않고 함께 싣되,
목표 판정에는 쓰지 않는다 — 셋을 나란히 둬야 정의를 사후에 갈아탄 사실이 눈에 보인다.

| 값 | 무엇을 재는가 | 왜 자동 완결률이 아닌가 |
|---|---|---|
| `firstPass` (`attempts=1` · 게이트 실패 0 · GREEN) | 한 번에 끝난 비율 | 재시도가 규약인 하네스에서 "자동으로 끝났는가"와 다른 질문이다 |
| `everGreen` (결국 GREEN) | 자동 완결률의 상한 | 사람이 BLOCKED를 푼 경우를 포함한다 — "자동"이라는 이름과 모순된다 |

### 태스크 계측률의 정의

- **분자** — `eval/loop-log.jsonl`에 엔트리가 있는 태스크 수 (= 자동 완결률의 분모)
- **분모** — `specs/tasks/T-*.md` 파일 수
- **산출기** — `tools/portfolio-metrics.ts`의 `backlog.instrumentedShare`

목표를 두지 않는다. 판정하는 지표가 아니라 **자동 완결률을 읽는 데 필요한 표본 크기**다.
완결률의 분모를 "계측된 태스크"로 좁힌 것이 계측 안 된 태스크를 없던 일로 만들지 않도록
이 지표가 같은 표에 함께 실린다. 두 수는 항상 같이 읽는다 — 계측률이 낮으면
완결률이 높아도 그것은 좁은 표본에 대한 값이다.
