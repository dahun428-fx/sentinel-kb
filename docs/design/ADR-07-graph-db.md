# ADR-07 — Graph DB 도입 검토

**상태**: 결정됨 — 단계적 채택 (지금은 그래프 "구조"만, 그래프 "DB"는 조건부)
**검토일**: 2026-08-21

## 1. 질문
그래프 DB(Neo4j 등) 도입이 sentinel-kb에 어떤 해결책 또는 더 나은 요소를 제공하는가?

## 2. 그래프가 실제로 잘 푸는 문제 — 이 도메인 기준

현재 검색(벡터+키워드)은 **표면 유사성**만 본다. "이 에러 텍스트와 비슷한 텍스트"는 찾지만,
"이 에러와 **같은 원인을 공유하는** 다른 증상"은 못 찾는다. 그래프가 여는 질의는 네 가지다.

| # | 질의 | 현재 | 그래프 |
|---|---|---|---|
| G1 | 다중 홉 인과: 에러 → 공유 원인 → 그 원인의 다른 증상들 → 공통 예방책 | 불가 (텍스트 유사성 한계) | 1~2홉 순회로 자연스럽게 해결 |
| G2 | 재발 사슬: 이 사건은 3개월 전 사건의 재발인가? 몇 번째인가? | 태그 겹침으로 추정만 | RECURRENCE_OF 엣지 체인으로 구조적 추적 |
| G3 | 허브 분석: 가장 많은 사건에 연결된 원인·라이브러리 = "가장 비싼 원인" 랭킹 | 태그 집계로 근사 | 연결 중심성으로 직접 계산 |
| G4 | 이격 구조 질의: 모델 M × 라이브러리 L 조합에서 반복되는 환각과 그 교정들 | divergence 텍스트 검색 | (모델)-(이격유형)-(대상API)-(교정) 경로 질의 |

특히 **G2·G3은 퍼블리싱 파이프라인(specs/08)의 팩트 추출기와 직결**된다. "우리는 왜 자꾸 X에서
넘어지는가"(패턴 아티클)의 소스가 태그 집계에서 인과 그래프로 바뀌면 글의 질이 달라진다.
G4는 이격 리포트("이 모델이 자주 틀리는 것들")를 통계 나열에서 구조 분석으로 끌어올린다.

## 3. 도입 비용 — 정직한 계산

| 비용 | 심각도 | 내용 |
|---|---|---|
| **엔티티 추출 파이프라인** | **최대 리스크** | 그래프는 저절로 생기지 않는다. 레코드 텍스트에서 원인·라이브러리·에러시그니처를 추출해 노드로 정규화해야 하는데, 이건 새로운 LLM 파이프라인이며 **추출이 틀리면 그래프가 오염**된다. 오염된 그래프는 오염된 골든셋처럼 조용히 전체를 망친다 |
| 온톨로지 유지 | 중 | 노드·엣지 타입 스키마를 설계하고 진화시켜야 함. "관계를 어디까지 쪼갤 것인가"는 끝없는 논쟁거리 |
| 인프라 추가 | 중 | Neo4j 도입 = 컨테이너+백업+학습+운영 항목 추가. "상태는 Atlas 하나"라는 현 운영 철학(ADR-04·06과 동일 논리) 훼손 |
| 정합성 이중화 | 중 | records(Mongo)와 그래프의 동기화 — 새로운 장애 지점 |
| 콜드 스타트 | 확정 | 레코드 수십~수백 건에서 중심성·커뮤니티 분석은 의미 없음. 그래프의 이점은 데이터 밀도의 함수 |

## 4. 결정 — 3단계 채택 경로

### 단계 0 (지금, M4~M5에 편입): 그래프 구조를 Mongo 안에서
- records에 **명시적 관계 필드** 추가:
  `relations: [{type: "recurrence_of"|"same_root_cause"|"related"|"corrects", targetRecordId, note?}]`
- 관계 생성 주체: 기록 시점에 에이전트/사람이 search 결과에서 링크 (record_knowledge 인자로 수용).
  **LLM 자동 추출이 아니라 기록자의 명시적 연결** — 오염 리스크를 원천 차단
- 탐색: Mongo `$graphLookup`으로 1~2홉 순회. suggest_resolution에 "관계 확장" 단계 추가 —
  벡터로 진입점을 찾고, 진입점의 relations 1홉을 컨텍스트에 병합 (경량 GraphRAG)
- G2(재발 사슬)와 G3 근사(관계 집계)가 이것만으로 열린다. **그래프 가치의 절반 이상을 인프라 0으로**

### 단계 1 (M7, 퍼블리싱과 함께): 엔티티 정규화
- 라이브러리·에러시그니처·모델을 별도 컬렉션으로 정규화 (결정론 추출 우선 + LLM 보조는 사람 승인)
- 팩트 추출기가 이를 소비 → G3·G4가 열림. 여전히 Mongo 안

### 단계 2 (조건부): 전용 그래프 DB
**판단 게이트 — 아래 셋 중 둘이 충족될 때만 착수:**
1. 레코드 500건 이상
2. $graphLookup 2홉 초과 질의가 실사용에서 주 5회 이상 필요해짐
3. 커뮤니티 탐지·중심성 등 그래프 알고리즘이 아티클 품질에 필요하다는 구체 사례 3건

충족 시 Memgraph/Neo4j를 **읽기 전용 파생 뷰**로 도입 (소스 오브 트루스는 계속 Mongo,
그래프는 재구축 가능한 캐시). 이렇게 하면 동기화 실패가 장애가 아니라 재빌드 사유가 된다.

## 5. 검증
- 단계 0의 효과는 측정한다: suggest_resolution의 관계 확장 on/off로 eval:retrieval·generation 비교.
  **확장이 지표를 올리지 못하면 단계 1로 가지 않는다** — 그래프도 다른 모든 것처럼 eval을 통과해야 한다
- 관계 필드 사용률(관계가 달린 레코드 비율)을 도그푸딩 지표에 추가 — 기록자가 실제로 연결하는지

## 6. 포트폴리오 관점
"그래프 DB를 썼다"보다 **"그래프 DB를 검토하고, 가치의 절반을 인프라 없이 취한 뒤, 도입 판단
게이트를 수치로 정의했다"** 가 더 강한 서사다. 기술 선택 능력은 도입이 아니라 도입 시점의 판단으로
증명된다.
