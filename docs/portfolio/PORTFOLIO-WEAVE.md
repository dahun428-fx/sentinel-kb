# 설계 고민을 소프트웨어와 포트폴리오에 녹이는 방법

원칙: **고민은 말로 남기면 주장이고, 시스템 안에 남기면 증거다.**
지금까지의 결정·전환·실수를 다섯 개 채널로 제품 안에 물리적으로 편입한다.

## 채널 1 — 결정의 자산화: ADR + 감사 보고서가 레포의 1급 시민
- `docs/design/ADR-01~07` + `docs/audit/AUDIT-REPORT.md`는 부록이 아니라 **검증 대상 문서**다.
  spec-drift-check가 ADR의 검증 가능한 주장(도구 5개, 의존 방향 등)을 CI에서 대조한다.
- 모든 PR 본문에 관련 결정 ID를 참조한다 (`refs: ADR-05, 감사 B-1`). 커밋 히스토리를 열면
  "무엇을"이 아니라 "왜"가 추적된다 — RTM이 요구사항을 추적하듯 결정을 추적한다.
- 전환의 기록을 지우지 않는다: v1 계획(UI 중심)과 v2(MCP 중심)를 모두 보존하고
  차이를 §0 변경표로 남겼다. **버린 설계가 남아 있어야 선택한 설계가 설득된다.**

## 채널 2 — 자기 시드: 개발 과정 자체가 첫 번째 데이터 (가장 강한 채널)
이 시스템의 존재 이유는 트러블슈팅·이격의 기록이다. 그렇다면 **이 시스템을 설계하며 실제로 겪은
사건들이 첫 시드**가 되어야 한다. `seed/self/`에 실사건 기반 레코드를 넣는다:

| 시드 | 타입 | 실제 사건 |
|---|---|---|
| SELF-01 | divergence | 임계값 단위 오류 — 스펙에 RRF 점수(최대 ~0.033)와 cosine 임계값(0.62) 비교를 기술. 감사에서 적발. correction: "융합 점수와 원시 유사도의 척도를 스펙에 명시하고, 게이트 판정 대상을 문장으로 못박는다" |
| SELF-02 | incident | 컨테이너 sh에서 brace expansion(`mkdir {a,b}`) 미동작 → 리터럴 디렉토리 생성됨. resolution: POSIX sh에선 개별 mkdir -p 사용 |
| SELF-03 | divergence | 루프 스크립트가 주석으로는 deps 검사를 주장하나 구현은 미검사 — 주석과 구현의 이격. correction: "주장은 반드시 실행 가능한 검증으로 강제한다" |
| SELF-04 | incident | nightly 리포트를 CI 아티팩트로만 저장 → 90일 후 소멸하는 설계. resolution: 시계열 자산은 저장소 커밋 |
| SELF-05 | divergence | RTM이 존재하지 않는 테스트 ID(IT-04·08) 참조 — 문서 간 참조 무결성 미검증. correction: 참조 대조를 CI 스크립트화 |

효과 세 가지: ① 시드 품질 문제(리스크 R1)를 실데이터로 해소, ② "자기 자신으로 자기를 개발"
서사의 물증, ③ 데모에서 "이 시스템에 뭐가 들었나요?" → "이 시스템을 만들다 겪은 것들"이라는
가장 강한 답변.

## 채널 3 — 감사의 상설화: 일회성 이벤트를 프로세스로
이번 감사(Critical 1건 적발)는 유효성이 증명됐다. 이를 하네스에 편입한다:
- `.claude/agents/auditor.md` — 정합성·실현가능성 겸임 감사 에이전트
- `/audit` 커맨드 — 마일스톤 종료마다 실행, 보고서를 `docs/audit/`에 누적
- 적발 사항 중 divergence 성격은 **자동으로 자기 시드 후보가 된다** (채널 2와 순환)

## 채널 4 — 퍼블리싱의 첫 발행물 = making-of 3부작
M7 파이프라인의 첫 아티클 소재를 외부 데이터가 아니라 자기 개발 기록으로 잡는다:
1. 케이스 스터디: "임계값 0.62가 모든 질의를 침묵시킬 뻔한 이야기" (SELF-01)
2. 패턴 아티클: "문서가 코드를 배신하는 세 가지 방식" (SELF-03·04·05 클러스터)
3. 이격 리포트: 개발 기간 divergence 기록 집계
파이프라인 데모와 콘텐츠 확보를 한 번에 해결하고, 글 자체가 기술 블로그 포스팅이 된다.

## 채널 5 — 경력 서사와의 접속
이 프로젝트의 메타 구조 — 스펙·게이트·감사·환류 루프로 **"AI가 일하는 개발 조직"을 설계하고
그 조직이 제품을 만들게 한 것** — 를 README 최상단 한 문단으로 명시한다. 개별 기능이 아니라
이 구조가 포트폴리오의 주장이다: 제품을 만들었고, 제품을 만드는 체계를 만들었다.

## README 서사 구조 (T-028에 반영)
```
1. 문제 — 지식은 왜 사라지는가 (+ AI 시대의 새 유실: 이격)
2. 결정 — ADR 7건 요약, 각 트레이드오프 한 줄
3. 전환 — v1→v2, 무엇을 버렸고 왜
4. 사고 — 감사가 잡은 Critical과 그것이 증명한 것
5. 지표 — eval 시계열 그래프, 루프 자동 완결률, 도그푸딩 실적
6. 재귀 — 자기 시드, 자기 발행물, 자기 개선 루프(/harvest)
```
