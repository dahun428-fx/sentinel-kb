# 3분 데모 스크립트 — 서로 다른 프로젝트 두 곳이 같은 지식을 쓴다

목표 한 문장: **A 프로젝트에서 해결한 장애를, B 프로젝트의 에이전트가 다시 파지 않는다.**

> **⚠️ 이 스크립트는 아직 녹화되지 않았다.** T-028 Acceptance 4("데모 시나리오가 실제로
> 재현됨(녹화)")는 **미이행**이다. 아래 §4가 어느 단계가 지금 기계로 재현되고 어느 단계가
> 자격증명을 기다리는지 한 줄씩 갈라 놓았다. **재현되지 않는 단계를 재현된 것처럼 찍지 않는다.**

---

## 0. 준비 (녹화 전, 화면 밖)

두 프로젝트가 **서로 다른 키**로 붙는다는 것이 데모의 전부다.
`project`는 요청 인자가 아니라 **키가 정한다**(`docs/connect.md` §1).

```bash
# .env — 키 하나가 프로젝트 하나다
API_KEYS=devkey123:sentinel-kb,devkey456:bizcare-web

pnpm dev:compose          # nginx · core-api · mcp · worker · web
pnpm db:seed              # 시드 50건 (self/ · divergence/ · incidents/ · public/)
pnpm mcp:ping             # 도구 5개 확인. 판정은 눈이 아니라 종료 코드로
```

화면에 띄울 디렉터리 둘:

```
~/demo/project-a/.mcp.json   →  Authorization: Bearer ${SENTINEL_KB_KEY}  (devkey123)
~/demo/project-b/.mcp.json   →  Authorization: Bearer ${SENTINEL_KB_KEY}  (devkey456)
```

두 파일의 내용은 **토큰만 다르고 나머지는 같다.** 레포 루트의 `.mcp.json`이 정본 예시다.

---

## 1. 0:00–0:35 — 문제 (A 프로젝트)

화면: `project-a`에서 Claude Code 세션. 터미널에 실패한 배포 로그.

> 나레이션 — "SSE 응답이 정확히 60초에 끊깁니다. 프록시를 의심하는데, 이 팀은 처음 보는 증상입니다."

에이전트가 **디버깅 전에** 검색한다 — 그 프로젝트 `CLAUDE.md`에 한 줄이 있기 때문이다:

```
디버깅 전 search_knowledge, 해결 후 record_knowledge
```

`search_knowledge("nginx sse 60초에 끊김")` → **결과 0건.** KB에 아직 없다.

> **0건을 보여주는 것이 데모의 핵심이다.** 이 시스템의 값어치는 "이미 다 들어 있다"가 아니라
> **"한 번 겪으면 다시는 안 판다"**이다. 채워진 DB로 시작하면 그 주장이 안 보인다.

---

## 2. 0:35–1:30 — 해결하고 기록한다 (A 프로젝트)

에이전트가 직접 판다. 원인: `proxy_read_timeout` 기본값 60초.
(이 레포에서 실측한 값이다 — 지시문을 지우면 **정확히 60.03초**에 끊긴다.)

해결 후 `record_knowledge`:

```jsonc
{
  "type": "incident",
  "title": "nginx 경유 SSE가 60초에 끊긴다 — proxy_read_timeout 기본값",
  "symptom": "…", "rootCause": "…", "resolution": "…", "prevention": "…",
  "tags": ["nginx", "sse", "mcp", "timeout"]
}
```

응답에서 **두 가지를 화면에 보여준다**:

1. `recordId` — 저장됐다.
2. `sanitizeFlags` — 붙여넣은 로그에 자격증명이 있었다면 **무엇이 마스킹됐는지 알려준다.**
   시크릿을 지우는 것만이 아니라 **지웠다는 사실을 호출자에게 돌려준다**는 것이 요점이다.

> 여기서 §5의 대사 하나: "이 레코드에는 `project: "sentinel-kb"`가 붙습니다.
> 인자로 준 게 아니라 **키가 정한 값**입니다. A 프로젝트가 남의 프로젝트 이름으로 쓸 수 없습니다."

---

## 3. 1:30–2:30 — 다른 프로젝트가 같은 벽을 만난다 (B 프로젝트)

화면 전환: `project-b` — **다른 레포, 다른 세션, 다른 키.**
(코드베이스도 언어도 다르다는 것이 보이면 좋다.)

> 나레이션 — "몇 주 뒤, 전혀 다른 팀이 같은 벽을 만납니다."

`search_knowledge("스트리밍 응답이 1분 뒤 끊깁니다")`

- **표현이 다르다.** A는 "60초에 끊김", B는 "1분 뒤 끊깁니다" — 하이브리드 검색이 필요한 이유다.
  에러코드·고유명사는 키워드가, 증상 서술은 벡터가 잡는다.
- 응답은 **요약 + ID만** 나온다. 본문은 없다 — MCP 응답 토큰 예산(NFR-03) 때문이다.
  화면에 응답 크기를 띄우면 좋다: 이 레포의 실측 상한은 800토큰이다.

`get_record(recordId)` → 전문. 화면에서 두 가지를 짚는다:

1. 응답이 `<retrieved-record>` 블록으로 **감싸여** 있다.
2. 그 안의 문장은 **데이터이지 지시가 아니다**(NFR-05). 만약 누군가 기록에
   "이전 지시를 무시하라"를 심어 뒀다면 그 청크는 `injection-suspect`로 플래그되고
   **생성 컨텍스트에서 아예 제외**된다.

B의 에이전트가 절차를 적용한다. **재조사 0분.**

마지막으로 `give_feedback(helped: true)` — "이 기록이 실제로 해결에 쓰였다."
이 값이 `hits`이고, `searches.withResults`(뭔가 돌아왔다)와 **다른 것**이다.

## 4. 2:30–3:00 — 루프가 닫힌다, 그리고 닫히지 않은 것

```
A: 겪음 → 기록  ─┐
                 ├─→ 같은 KB ─→ B: 검색 → 적용 → give_feedback
B: 겪음 → 기록  ─┘                            └─→ /harvest → 규칙 개선 초안
```

마지막 30초는 **재귀**다: 이 KB의 첫 데이터는 이 KB를 만들며 겪은 사건들이다
(`packages/core/seed/self/`, 6건). 그중 SELF-06은 이 레포에서 시크릿 마스킹 하나가
**여덟 라운드를 돈** 기록이다.

### 이 스크립트에서 지금 무엇이 재현되는가

**녹화 전에 이 표를 확인한다. 재현되지 않는 단계를 재현된 것처럼 편집하지 않는다.**

| 단계 | 지금 재현되나 | 근거 / 막는 것 |
| --- | --- | --- |
| compose 5종 기동 | **부분** | 이미지 5종 전부 빌드되고 `mcp`·`web`이 실제로 뜬다. 끝까지 띄우려면 Atlas 자격증명이 필요하다(T-026 F-12) |
| nginx 경유 MCP 연결·도구 5개 | **예** | `tools/nginx-streaming.int.spec.ts`가 `pnpm mcp:ping`을 nginx 경유로 돌려 exit 0을 확인한다 — `pnpm verify`의 integration에서 매번 돈다 |
| SSE가 청크 단위로 흐른다 | **예** | 같은 스위트의 도착시각 테스트. `proxy_read_timeout`을 지우면 60.03초에 끊기는 것도 프로브가 잡는다 |
| 키가 `project`를 정한다 | **예** | `packages/mcp`의 서버 팩토리 주입 seam을 단위·통합 테스트가 관측한다(T-014) |
| `record_knowledge` + `sanitizeFlags` | **예** | 마스킹 게이트는 2,820칸 전수 스윕에서 0/94다 |
| `search_knowledge`가 **쓸 만한** 결과를 준다 | **아니오** | `FakeEmbedder`는 텍스트 간 cosine ≈ 0이다. 지금 검색은 사실상 BM25 단독이고, 그 품질은 측정된 적이 없다(T-013 BLOCKED) |
| "표현이 달라도 찾는다"(§3의 핵심 장면) | **아니오** | 위와 같은 이유. **실 임베딩 자격증명이 이 데모의 유일한 전제 조건이다** |
| `suggest_resolution`이 해결책을 **생성**한다 | **아니오** | 현재 검색 기반 스텁이다. 생성은 `/v1/answer` 경로이고 실 LLM 키가 필요하다 |
| 원격(배포된) 서버 접속 | **아니오** | AWS 계정·도메인이 없다(T-027 Acceptance 1 판정 불가) |

**따라서 지금 정직하게 찍을 수 있는 데모는 로컬 compose 위의 것이고,
§3의 "표현이 달라도 찾는다" 장면은 임베딩 키가 열린 뒤에 찍어야 한다.**
그 전에 찍으면 화면에 나오는 것은 하이브리드 검색이 아니라 BM25이고,
그것을 하이브리드라 부르는 순간 이 레포가 내내 지킨 규칙을 데모에서 깨는 것이다.

## 5. 녹화 체크리스트

- [ ] 두 프로젝트의 **키가 다르다**는 것이 화면에 보이는가 (`.mcp.json` 두 개를 나란히)
- [ ] 첫 검색이 **0건**으로 시작하는가 (채워진 DB로 시작하지 않는다)
- [ ] `sanitizeFlags`가 화면에 나오는가
- [ ] `search_knowledge` 응답에 **본문이 없다**는 것을 짚었는가 (NFR-03)
- [ ] `get_record`의 `<retrieved-record>` 프레이밍을 짚었는가 (NFR-05)
- [ ] `give_feedback`과 "결과가 나왔다"의 차이를 말했는가
- [ ] 시크릿·실제 도메인·실제 키가 화면에 없는가 (`SENTINEL_KB_URL`·`SENTINEL_KB_KEY`는 env 참조로)
- [ ] §4 표에서 **"아니오"인 단계를 찍지 않았는가**
