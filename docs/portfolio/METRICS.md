# 루프 계측 회고 — 28줄이 말하는 것

원천은 `eval/loop-log.jsonl` 하나다. `.claude/skills/task-loop/SKILL.md` §7이 정한
append-only 로그이고, 태스크 한 라운드가 한 줄이다.

집계 표(완결률·게이트 분포 등)는 **README §6-1에 있고 손으로 쓰지 않았다** —
`tools/portfolio-metrics.ts`가 산출하고 `tools/portfolio-docs.spec.ts`가 매 `pnpm verify`마다
재계산해 대조한다. 이 문서는 그 표가 답하지 않는 것, 즉 **왜 그런 값이 나왔는가**를 다룬다.

```bash
pnpm exec tsx tools/portfolio-report.cli.ts   # 지표 재산출 (eval/reports/ 에 쓴다)
```

---

## 1. 먼저: 이 로그로 잴 수 있는 것과 없는 것

**잴 수 있다** — 완결률(정의를 명시하는 한), 게이트 실패 분포, attempts 분포,
PLAN 선언 여부, Context budget 규모, 계측 자체의 결함.

**잴 수 없다** — 인과. 표본이 25개 태스크이고, 각 태스크는 난이도·검증자·스코프가 전부 다르다.
"규칙 X를 넣었더니 성공률이 올랐다"는 이 로그로 **주장할 수 없다.** 아래 §4에서 관측된
공기(co-occurrence)를 적되 인과로 쓰지 않는 이유다.

**로그에 아예 없다** — 백로그 41개 태스크 중 **25개만 기록됐다.** T-017·T-018·T-023~T-036·T-038은
로그 줄이 없다. 이것은 "실패했다"가 아니라 **"계측되지 않았다"**이고,
따라서 완결률의 분모는 프로젝트 전체가 아니라 **계측된 부분**이다. 분모를 부풀리거나
줄이는 대신 그 사실을 여기 적는다.

## 2. 완결률의 정의가 스펙에 없다

`specs/00-product.md` 성공 지표는 "태스크 자동 완결률 >= 70%" 한 줄이고 **분자·분모를 정하지 않았다.**

정의를 하나만 고르면 **가장 좋아 보이는 정의를 고를 유인**이 생긴다. 실제로 이 로그에서
세 정의의 값은 **24.0% / 72.0% / 76.0%**로 갈린다 — 어느 것을 "그" 값이라 부르느냐가
목표 70% 달성 여부를 뒤집는다. 그래서 셋을 전부 싣는다(README §6-1).

| 정의 | 무엇을 세는가 | 사람의 개입 |
| --- | --- | --- |
| 한 번에 | `attempts = 1` · 게이트 실패 0 · 최종 GREEN | 없음 |
| 재시도 한도 안 | 최종 GREEN · `attempts <= 3` | 없음(루프 규약 안) |
| 결국 GREEN | 최종 GREEN | **T-004는 사람이 BLOCKED를 풀었다** |

**셋의 차이가 곧 개입의 양이다.** 그리고 세 번째 정의는 "자동"이라는 말과 이미 어긋나 있다 —
그것을 70% 판정에 쓰면 지표가 자기 이름을 배신한다.

> **이 문서는 목표 달성을 선언하지 않는다.** 정의가 스펙에 없는 상태에서 달성을 선언하는 것은
> 사후에 유리한 자를 고르는 일이다. 정의를 확정하는 것은 사람의 몫이고
> `docs/DECISIONS-PENDING.md`에 올려 뒀다.

## 3. BLOCKED·PARTIAL의 사유 분포 — 한 건만 코드 문제다

로그의 `status`와 태스크 파일의 `STATUS:`를 함께 보면 막힌 태스크는 일곱이다.

| 태스크 | 무엇이 막았나 | 종류 |
| --- | --- | --- |
| **T-004** | 열거 기반 fail-open. 여덟 라운드, 재시도 한도 3회를 세 번 초과 | **코드·설계** |
| T-013 | 실 임베딩 자격증명 부재 → `Recall@5` 측정 자체가 불가 | 외부 자원 |
| T-016 | tool-calling 가능한 provider와 러너가 만난 적 없음 | 외부 자원 |
| T-020 | judge 모델 키 부재 | 외부 자원 |
| T-021 | 방어선 3(프롬프트 내성)에 실 `ChatModel` 필요 | 외부 자원 |
| T-040 | 평문 지시문 축의 대안(의미 계층)에 임베딩 자격증명 필요 | 외부 자원 |
| T-028 | eval 리포트가 0건이라 "전/후 비교 그래프"를 그릴 데이터가 없다 · 데모 녹화도 같은 벽 | 외부 자원 |

**일곱 중 여섯이 같은 벽이다: 자격증명이 없어 지표를 잴 수 없다.**
이 분포는 "무엇을 더 만들어야 하는가"보다 **"무엇을 열어 줘야 하는가"**를 가리킨다.
`docs/DECISIONS-PENDING.md` §1이 그 열쇠 하나(임베딩 자격증명)를 최우선으로 올린 근거다.

그리고 T-040은 막혔다는 사실을 **코드에 선언**했다 — `KNOWN_STRUCTURAL_GAPS`에 두 축을 적고,
테스트가 그 목록의 크기가 늘지 않음을 단언한다. 못 닫은 것을 못 닫았다고 적는 것이
숫자를 올리는 것보다 낫다는 판단의 실물이다.

## 4. 게이트가 말하는 것

| 게이트 | 실패 엔트리 | 읽는 법 |
| --- | --- | --- |
| G1 정적 | 1 | lint·typecheck는 거의 즉시 잡힌다 — 값싼 게이트다 |
| G2 테스트 | 7 | **가장 많이 걸렸다.** 그중 3건이 T-004다 |
| G3 계약 | 0 | contracts breaking change가 한 번도 시도되지 않았다 |
| G4 Eval | 0 | **좋은 소식이 아니다** — eval이 실데이터로 돌아 본 적이 없다 |
| G5 스펙정합 | 5 | 전부 초기 태스크. §4-1 |
| G6 MCP계약 | 0 | 도구 5개가 한 번 정해진 뒤 바뀌지 않았다 |

**G4가 0인 것을 "회귀가 없었다"로 읽으면 안 된다.** `pnpm eval:retrieval`·`eval:tools`·
`eval:generation`·`eval:injection`은 전부 자격증명이 없어 exit 78로 거절한다.
**작동한 적 없는 게이트와 통과한 게이트는 로그에서 똑같이 `0`으로 보인다** —
이 구별을 로그가 못 한다는 것 자체가 계측의 결함이고 §6에 적는다.

### 4-1. G5 5건이 전부 초기에 몰려 있다 — 인과가 아니라 관측이다

G5(스펙 정합) 실패 5건은 T-002·T-003·T-007·T-008·T-011이고 **전부 2026-08-22 이전**이다.
그 뒤로 로그된 12개 태스크에서는 0건이다.

그 사이에 있었던 일: T-010·T-011·T-012에서 **"태스크 스펙이 스스로 모순됐다"**가 세 번
연속 났고(Findings가 고치라고 지시한 파일을 Context budget이 배제), `task-loop` 스킬에
**budget 자동 포함 5항** + "오케스트레이터 지시와 태스크 스펙이 충돌하면 멈춰라"를 명문화했다.

**이것을 "규칙이 성공률을 올렸다"로 쓰지 않는다.** 같은 기간에 바뀐 것이 최소 셋 더 있다 —
태스크의 성격(기반 → 응용), 검증 프로토콜(축 인계 요구), 그리고 구현자가 읽는 파일 수가
중앙값 11에서 18 이상으로 늘었다. 25개 표본에서 이들을 가를 수 없다.
**적을 수 있는 것은 "G5 5건이 모두 그 규칙 이전에 있었다"까지다.**

### 4-2. 그러나 스펙 서술에 대해 근거를 갖고 말할 수 있는 것이 하나 있다

T-004의 포스트모템이 낸 진단은 표본이 아니라 **메커니즘**에 근거한다:

> 스펙이 마스킹 대상을 **유형 목록**으로 줬다(`T-004:39`). Acceptance도 **케이스 수**였다
> ("마스킹 케이스 12개 유닛 테스트 통과"). 목록은 자연히 목록형 구현을 부르고,
> 그 구현의 검증도 자연히 "목록에 있는 케이스"가 된다.
> **Acceptance가 12개 케이스인 이상, 13번째를 찾는 것은 Acceptance 밖이다.**

같은 파일 안에 대조군이 있다는 점이 이 진단을 실측으로 만든다 — 비가시 문자 축은
같은 스펙 문장에서 나왔는데 **판정 근거를 유니코드 범주로 옮겨** 4라운드 만에 닫혔다.
그리고 그 축의 프로퍼티 생성기는 **구현이 모르던 축(짝 없는 서로게이트 `Cs`)을 즉시 찾아냈다.**

**따라서 "어떤 스펙 서술이 성공률을 올리는가"에 대한 이 레포의 답은 이것이다:**
Acceptance를 **케이스 수**로 쓰면 구현과 검증이 둘 다 그 수에 최적화된다.
**불변식**으로 쓰고, 판정 실패 시의 기본 동작(fail-open인가 fail-closed인가)을 스펙에 명시해야 한다.

## 5. 비용은 균등하지 않다

`attempts` 합 56회 중 **T-004 한 태스크가 19회(33.9%)**다.
엔트리 28줄 중 T-004가 3줄이니, **줄 수의 11%가 비용의 33.9%**를 썼다.

`filesRead`는 초기 5~12개에서 후기 17~43개로 늘었다(최대는 T-019의 43).
Context budget이 커진 것을 "규율이 느슨해졌다"로 읽을 수도 있고
"태스크가 시스템 후반부로 갈수록 접점이 많아졌다"로 읽을 수도 있다.
로그는 둘을 구별하지 못한다 — `filesRead`가 **budget 안이었는지**를 기록하지 않기 때문이다(§6).

## 6. 계측 자체의 결함 — 기계가 4건을 찾았다

`tools/portfolio-metrics.ts`가 `anomalies`로 싣고, README §6-1의 표가 그 건수를 인용한다.

| 결함 | 무엇이 안 보이게 되나 |
| --- | --- |
| `T-001`에 `planLines`·`filesRead`가 없다 | PLAN 선언과 budget 준수를 **기계 판정할 수 없다** (T-000 F-2가 예고한 그대로) |
| `T-019`·`T-039`의 `status`가 `done` | 규약 어디에도 없는 값. 집계기가 조용히 GREEN으로 접으면 그 불일치가 영영 안 보인다 |

**로그에 없어서 기계가 못 잡는 결함이 셋 더 있다** — 정직하게 적는다:

1. **로그의 `status`와 태스크 파일의 `STATUS:`가 어긋난다.** T-013·T-016은 로그가 `PARTIAL`,
   파일이 `BLOCKED`다(T-013은 `note`에 "STATUS는 BLOCKED 유지"라고 적어 스스로 모순을 신고했다).
   반대로 T-020·T-021·T-040은 로그가 `PARTIAL`인데 **파일에 `STATUS:` 줄이 아예 없다.**
2. **`filesRead`가 budget 준수 여부를 담지 않는다.** 파일 목록만 있고 "그것이 budget 안이었는가"는
   없다. T-010·T-020이 실제로 budget을 벗어났다는 사실은 `note` 산문에만 있어 집계되지 않는다.
3. **`approachChanges`가 없다.** 포스트모템 §5.2의 제안이다 —
   `attempts: 8, approachChanges: 1`과 `attempts: 8, approachChanges: 6`은 **전혀 다른 사건**인데
   지금 로그는 둘을 구별하지 못한다. T-004가 정확히 전자였다.

셋 다 스킬 규약 변경이라 이 태스크의 범위 밖이고, `docs/DECISIONS-PENDING.md`에 올려 뒀다.
