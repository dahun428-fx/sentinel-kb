# 기여 규약 — 결정을 추적 가능하게 남긴다

이 레포는 **커밋 히스토리를 열면 "무엇을"이 아니라 "왜"가 나오는 것**을 목표로 한다.
RTM이 요구사항을 추적하듯 PR이 **결정**을 추적한다.

에이전트가 지킬 구현 규약은 `CLAUDE.md`와 `.claude/skills/task-loop/SKILL.md`에 있다.
이 문서는 그 위에 얹히는 **PR·커밋 규약**만 다룬다.

---

## 1. 한 태스크 = 한 세션 = 한 PR

브랜치는 `feat/T-xxx-<slug>`. 태스크에 없는 개선은 하지 않는다 —
발견하면 그 태스크 파일의 `## Findings`에 적고 넘어간다.

Findings에 적는 것이 미루는 것이 아니다. 이 레포에서 **T-036·T-038·T-039·T-040은 전부
다른 태스크의 Findings에서 태어났다.** 적힌 것만 백로그가 된다.

---

## 2. PR 본문에 결정 ID를 참조한다

**본문 첫 줄은 `refs:`다.** 관련된 결정·감사 항목·Findings를 전부 적는다.

```
refs: ADR-05, 감사 B-1, T-011 F-9, specs/03 §4
```

### 참조할 수 있는 ID

| 접두 | 무엇 | 어디 |
| --- | --- | --- |
| `ADR-01` … `ADR-06` | 아키텍처 결정 | `docs/design/SAD.md` 결정 표 |
| `ADR-07` | Graph DB 단계적 채택 | `docs/design/ADR-07-graph-db.md` |
| `감사 A-n` / `감사 B-n` | 감사 적발 항목 (A=정합성·추적성, B=실현가능성·보안) | `docs/audit/AUDIT-REPORT.md` |
| `T-xxx F-n` | 그 태스크의 Findings 항목 | `specs/tasks/T-xxx-*.md` |
| `T-xxx D-n` / `R-n` | 그 태스크에서 내린 결정 / 남긴 리스크 | 같은 곳 |
| `FR-nn` / `NFR-nn` | 요구사항 | `specs/00-product.md` |
| `specs/NN §M` | 스펙 조항 | `specs/` |
| `SELF-nn` / `DIV-nn` | 시드 레코드 (divergence·incident) | `packages/core/seed/` |

**댈 것이 없으면 그것이 신호다.** 어느 결정에도 걸리지 않는 변경은
(a) 스코프 밖이거나 (b) 아직 결정되지 않은 것을 구현하고 있다.
후자라면 멈추고 `docs/DECISIONS-PENDING.md`에 올린다.

### 본문의 나머지

`.claude/skills/task-loop/SKILL.md` §6이 정한 네 절을 그대로 쓴다:

```markdown
refs: <결정 ID들>

## Acceptance
항목별 충족 근거. **판정 불가면 "판정 불가"라고 적는다** — 통과로 적지 않는다.

## 변경 파일
Context budget 밖 파일을 건드렸다면 그 사실과 이유를 여기 적는다(G5 판정 대상).

## Findings
스코프 밖에서 발견한 것. 다음 태스크의 씨앗이다.

## eval diff
해당하면 기준선 대비. **기준선을 낮추는 커밋은 받지 않는다.**
```

---

## 3. 커밋 메시지

- 제목: 영어 동사로 시작하는 한 줄. `T-xxx: <한국어 요약>` 또는 `Fix: <한국어 요약>`.
- 본문은 영어·한국어 어느 쪽이든 좋으나 **왜**를 적는다. 무엇을 바꿨는지는 diff가 안다.
- 한국어 산문(문서·주석), 영어 코드(식별자). `CLAUDE.md` 코드 규칙과 같다.

---

## 4. 머지 전에 반드시

```bash
pnpm verify     # lint + typecheck + unit + integration. 그린이 아니면 PR을 열지 않는다
```

`pnpm verify`가 **워킹 트리를 검증하지 커밋될 내용을 검증하지 않는다**는 점을 기억한다.
T-027 F-0에서 실제로 났다 — 머지 충돌 마커가 커밋된 `package.json`이 로컬에서는 그린이었다.
**커밋 뒤 깨끗한 체크아웃에서 한 번 더 도는 것은 CI의 몫이다.**

게이트 6개 중 셋은 자동 재시도가 아니라 **사람의 승인**을 요구한다:

| 게이트 | 무엇 | 실패 시 |
| --- | --- | --- |
| G3 계약 | `packages/contracts` breaking change | **BLOCKED — 인간 승인** |
| G4 Eval | 기준선 미달 | 분석 후 1회 재시도, 이후 BLOCKED |
| G6 MCP 계약 | 도구 스키마·description 변경 | **BLOCKED — 인간 승인** |

## 5. 하지 않는 것

- **테스트·eval·`eval/baselines.json`을 고쳐서 통과시키기.** 즉시 중단 사유다.
  기준선 하향은 사람만 결정한다.
- **측정하지 않은 값을 성과로 적기.** 문서에도 PR 본문에도 해당한다.
  `tools/portfolio-docs.spec.ts`가 README에 대해서는 이것을 기계로 막는다.
- **뮤테이션 생존자를 숨기기.** 보고에는 **각 뮤테이션이 어느 관측 경로로 죽는지**를 적는다.
  T-014에서 "생존 0" 보고가 반증됐고, T-027에서는 생존자를 정직하게 적은 것이
  롤백 체계 전체가 무효라는 사실을 찾아냈다.
- **스펙 없는 API·MCP 도구 추가.** 도구는 5개에서 늘지 않는다(`specs/07`).
- **시크릿 하드코딩.** SSM/`.env`만.

---

## 6. 스펙과 코드가 어긋났을 때

**코드가 아니라 스펙을 먼저 고친다** — 그리고 그것은 인간 승인 사항이다(`CLAUDE.md` 원칙 1).
에이전트가 할 수 있는 것은 어긋남을 그 스펙 파일에 인용 블록으로 적고
`docs/DECISIONS-PENDING.md`에 올리는 것까지다.

`specs/03-rag-pipeline.md`에 `> T-005 정정(인간 비준 대상)` 같은 블록이 여럿 있는 것이
이 절차의 흔적이다. **정정 제안이 스펙 본문 옆에 남아 있어야 나중에 왜 바뀌었는지가 보인다.**
