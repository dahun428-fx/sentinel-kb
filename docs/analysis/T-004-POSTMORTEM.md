### 1.1 N-13의 실제 크기 — 이번에 처음 측정했다

태스크 파일은 N-13을 "`mongodb://tokenonly@host` 형태"라고만 적었다. 대역을 재 봤다.

기저 입력 `mongodb://tok{C}enngPassAbc123@cluster0.example.net/db`, `{C}`에 ASCII 인쇄 가능 94자를 하나씩:

| 축  | 무엇을 훑는가                   | 어느 라운드 표가 덮었나          | **현행 유출** |
| --- | ------------------------------- | -------------------------------- | ------------- |
| 축1 | 비밀번호 **안**의 문자          | 6차 표 (`sanitize.spec.ts:870`)  | 0/94          |
| 축2 | 호스트 **뒤**의 문자            | 7차 표 (`sanitize.spec.ts:1082`) | 0/94          |
| 축3 | 비밀번호 안 **`@` 뒤**의 문자   | 8차 표 (`sanitize.spec.ts:1156`) | 0/94          |
| 축4 | **`:` 없는 사용자명 안**의 문자 | **어느 표도 안 덮음**            | **93/94**     |
| 축5 | 스킴 직후 문자                  | 없음                             | 0/94          |
| 축6 | `:` 있는 사용자명 안의 문자     | 없음                             | 0/94          |

실측 스크립트: `findUserinfoEnd`(`masking.ts:274`)를 그대로 복제해 축별로 94회 호출.
93/94는 "94자 중 `:` 하나를 제외한 전부"다 — `:`가 들어가면 lenient 갈래가 켜지기 때문이다.

실제 파이프라인 확인 (`sanitize()` 직접 호출):

```
현행: "mongodb://tokenonly_abcdef123456@cluster0.example.net/db"      flags=[]
현행: "mongodb+srv://ops.corp.com@cluster0.example.net/db"            flags=[]
```

두 번째는 Atlas의 이메일형 사용자명이다. 토큰을 사용자명 자리에 넣는
`mongodb://<apikey>@host` 형태도 같은 대역에 있고, F-19의 "사용자명 단독은 민감도가 낮다"는
근거가 이 대역에서는 성립하지 않는다.

## 2. 근본 원인 — 왜 매번 열거로 갔는가

"매번 열거를 고쳤다"는 7차 검증이 이미 낸 진단이다. 그 아래를 판다.

### 2.1 원인 A — 스펙이 마스킹 대상을 **유형 목록**으로 줬다 (증거 있음)

`specs/tasks/T-004-sanitizer.md:39`:

> 마스킹: AWS 액세스키/시크릿, Bearer 토큰, `sk-`류 API 키, mongodb+srv URI의 자격증명, 이메일(옵션), 사설 IP는 유지

`specs/00-product.md:23` (FR-06)은 한 줄이다: "새니타이즈 게이트: 시크릿 마스킹, 인젝션 의심 텍스트 플래그".
Acceptance는 `마스킹 케이스 12개 유닛 테스트 통과`(`:47`) — **케이스 수**로 표현돼 있다.

스펙이 준 것은 "무엇을 가려야 하는가"의 **목록**이고, 불변식이 아니다. 목록은 자연히 목록형 구현
(정규식 + 문자 클래스)을 부르고, 그 구현의 검증도 자연히 "목록에 있는 케이스"가 된다.
**Acceptance가 12개 케이스인 이상, 13번째를 찾는 것은 Acceptance 밖이다.**

다만 이 인과를 과대평가하면 안 된다. **같은 스펙 문장에서 파생된 비가시 문자 축은
범주 기반으로 탈출했다**(§3). 스펙 형태는 초기 조건이지 결정 요인이 아니다.
결정 요인은 아래 B·C다.

### 2.2 원인 B — 검증이 "케이스"를 넘겨 국소 최적화를 강제했다 (증거 있음)

Findings에 남은 검증 인계 형태를 보면 전부 **구체 케이스 목록**이다:

- 4차: "N-8 … 룩어헤드 변형 3종 실측: 룩어헤드 없음 → 미탐 0/5·오탐 2/2"
- 5차: "mongo 자격증명 미탐 **7종**으로 RED"
- 6차: "N-11 실측 유출 … ASCII 인쇄 가능 94자 중 **25자**"
- 7차: "실측 41종"
- 8차: "N-12 58종 유출 0"

구현자는 매번 그 N종을 통과시키는 **최소 수정**을 했고, 그때마다 통과했다.
케이스 목록을 받으면 케이스를 닫는 것이 합리적 행동이다 — 문제는 케이스가 **축의 표본**인데
축이 인계되지 않았다는 것이다. 7차 검증이 처음으로 축("열거 기반 판정")을 인계했고,
그 라운드에서만 구조적 제거(호스트 모양 검증 삭제)가 일어났다.

**즉 접근을 바꾼 것은 구현자가 아니라 검증자였다.** 이것이 §5의 프로토콜 제안 두 개의 근거다.

### 2.3 원인 C — 테스트 축을 "직전에 지적받은 자리"에서 골랐다 (증거 있음)

세 개의 대역 스윕 표는 전부 "직전 라운드가 열린 자리"를 기저로 삼았다:

| 표  | 위치                    | 기저 입력                                             | 훑은 축             | 놓친 자리                |
| --- | ----------------------- | ----------------------------------------------------- | ------------------- | ------------------------ |
| 6차 | `sanitize.spec.ts:870`  | `…:Str0ngPass{C}x@host…` (기저 비번에 **`@`가 없다**) | 비밀번호 안 문자    | 호스트 뒤                |
| 7차 | `sanitize.spec.ts:1082` | `…:Str0ngPass@host{C}`                                | 호스트 뒤 문자      | 비번 안 `@` 뒤           |
| 8차 | `sanitize.spec.ts:1156` | `…:P@ssw0rd{C}…@host…`                                | 비번 안 `@` 뒤 문자 | **`:` 없는 사용자명 안** |

축 선택의 규칙이 "지적받은 케이스의 좌표를 일반화한다"였기 때문이다. 그러면 축은 언제나
**직전 실패의 이웃**이 되고, 원리적으로 한 칸씩만 이동한다. 이번에도 그랬다 — 축4는
직전 실패(N-12)의 이웃이 아니라 **갈래 진입 조건**이라, 세 표 어디에도 없다(§1.1 실측 93/94).

축을 고르는 옳은 방법은 실패의 좌표가 아니라 **입력 문법의 구조**에서 뽑는 것이다.
mongodb URI의 문법 위치는 `scheme / user / [":" pass] / "@" / host / [":" port] / path / query`이고,
축은 그 **위치의 개수**만큼 있다. 세 표는 그중 3개를 덮었고 6개를 안 덮었다.

### 2.5 종합 — 제거되지 않은 성질 하나

여덟 라운드 내내 살아남은 성질은 이것이다:

> **판정용 열거에 없는 문자를 만나면 규칙이 무발동하고, 무발동은 무플래그 평문 통과를 뜻한다.**

즉 **fail-open**이다. 열거를 고칠 때마다 열거는 정확해졌지만 fail-open은 그대로였고,
열거는 원리적으로 유한하므로 다음 형제 문자가 언제나 남아 있었다.
`masking.ts:257-268`의 주석이 이 성질을 정확히 서술하고도 **제거는 하지 않았다**:

> 열거에 없는 문자 = 조용한 유출이라는 성질은 여섯 라운드 내내 제거되지 않았다.
> 그래서 모양 검증을 통째로 걷어냈다.

호스트 쪽 열거 하나를 지웠을 뿐 fail-open 자체는 남았고, 그래서 N-12·N-13이 이어졌다.

## 3. 대조 분석 — `invisible.ts`는 어떻게 벗어났는가

비가시 문자 축도 **네 번** 같은 실패를 했다: F-8 → N-2 → N-6 → N-9.
지금은 `sanitize.property.spec.ts`가 전 평면(0x0–0x10FFFF)을 훑어 표집하고 미탐 0이다.
차이를 셋으로 분해하고 각각의 기여도를 판정한다.

| #   | 무엇이 바뀌었나                                                                               | mongo 축에 이식 가능? | 판정     |
| --- | --------------------------------------------------------------------------------------------- | --------------------- | -------- |
| ①   | 판정 기준이 **문자 목록 → 유니코드 속성** (`invisible.ts:99-109`)                             | **불가**              | 아래 3.1 |
| ②   | 프로퍼티 생성기가 **구현이 아니라 속성에서 표집** (`property.spec.ts:135-253`)                | **가능**              | 아래 3.2 |
| ③   | 검증이 **독립 오라클로 전수 스윕** (`Cf`이면서 `Default_Ignorable`이 아닌 29종을 찾아낸 방식) | **가능**              | 아래 3.3 |

### 3.1 ①은 이식할 수 없다 — 그리고 그게 진짜 대비다

`invisible.ts`가 쓸 수 있었던 것은 유니코드가 **외부에서 제공하는 전칭 술어**다.
`\p{Cf}`는 "이 문자가 서식 문자인가"를 구현과 무관하게 판정한다. 열거를 속성으로 바꾸면
형제 문자가 자동으로 들어온다 — `invisible.ts:41`이 "범주 전체를 덮으면 열거가 필요 없어지고
형제 문자가 더 나오지 않는다"고 쓴 그대로다.

**mongo 축에는 그런 술어가 없다.** "이 문자열이 자격증명인가"를 판정하는 외부 표준은 존재하지 않는다.
RFC 3986의 `userinfo` 문자집합은 있지만, N-10이 보여 준 대로 실제 기록의 비밀번호는
그 집합을 이스케이프 없이 벗어난다(`?`·`/`·`@`). RFC를 채택하면 그것도 그냥 또 하나의 열거다.

따라서 **①은 대비의 결론이 아니라 대비의 원인**이다:
비가시 축은 "전칭 술어가 존재하는 문제"였고 mongo 축은 아니었다.
mongo 축이 얻을 수 있는 것은 ①의 형태가 아니라 ①의 **효과** — "열거가 판정하지 않게 하는 것" — 이고,
전칭 술어가 없을 때 그 효과를 내는 유일한 수단은 **fail-open을 fail-closed로 뒤집는 것**이다(§4).

### 3.2 ②는 이식 가능하고, 결정적이었다

②의 핵심은 "무엇을 생성할지"를 구현이 정하지 않게 한 것이다.
`property.spec.ts:116-121` 주석이 규칙을 명문화했다:

> 여기서는 **구현이 무엇을 지우는지 보지 않고** 표집한다.
>
> 1. 유니코드 General_Category를 런타임 `\p{...}`로 직접 열거한다. `invisible.ts`를 import하지 않는다.
> 2. 거기에 **전 평면 무작위 표집**을 섞는다.

기여도의 증거는 Findings에 실측으로 남아 있다:

> `\p{Cf}` 확대를 되돌리면 **프로퍼티 3개가 죽는다.** 같은 뮤턴트에 구 생성기는 22개 전부 통과했다.
> — F-17이 "선언"이 아니라 실측으로 닫혔다.

그리고 이 생성기는 **구현이 몰랐던 축을 새로 찾아냈다**: `Cs`(짝 없는 서로게이트).
결정 2는 `Cf`·`Cc`만 지목했는데 생성기가 `Cs` 구멍을 즉시 찾아 결정 3에 함께 닫혔다
(`invisible.ts:55-65`). **표본이 구현을 넘어야 구멍을 찾을 수 있다**는 명제의 실증이다.

mongo 축에 이식하면 이렇게 된다: 생성기가 **URI 문법 위치별로** 값을 뽑고
(scheme / user / pass / 구분자 / host / port / path / query / URI 뒤 문자),
각 위치의 알파벳을 "구현이 허용하는 문자"가 아니라 **"실제 기록에 나타날 수 있는 문자"**
(ASCII 인쇄 가능 94자 + 유니코드 공백류 + CJK + 이모지)에서 뽑는다.
그러면 축4는 "pass 위치를 생성하지 않는 분기"로 자동 생성된다.

**판정: ②가 결정적이었다. 그대로 이식 가능하고, 이식해야 한다.**

### 3.3 ③은 이식 가능하지만 ②의 부수 효과다

N-9의 29종을 찾아낸 것은 "6,548 코드포인트 스윕"이다. 이것은 ②의 생성기가 하는 일과 같고,
독립 오라클(`Cf`라는 다른 속성 축)로 전수 스윕했기에 `Default_Ignorable` 기준의 구멍이 드러났다.

mongo 축의 대응물은 §1.1에서 내가 실제로 한 것이다 — **문법 위치 × ASCII 94자 전수**.
축4를 93/94로 찾아낸 방법이 그것이고, 6·7·8차의 표 세 개는 이 스윕의 부분집합이었다.
전수 스윕은 이미 이 레포의 관행이므로 ③은 새 기법이 아니라 **적용 범위의 문제**다.
문법 위치를 6개 놓쳤을 뿐이다.

**판정: ③은 ②를 이식하면 따라온다. 단독 조치로는 다음 라운드에 또 한 칸 옆을 훑을 것이다.**

### 4.0 전제 확인 — `new URL()`은 mongodb 스킴을 파싱하는가 (실측)

Node v22.22.2, `new URL(input)` 직접 호출:

| ------------------------------------------------------------------------------ | ----------------------------------------------------------------- |

| `mongodb://localhost:27017 에서 실패, @team 에 공유했다.` (F-15)               | **THROW** ✅                                                      |

**세 가지 결론:**

1. **스킴 자체는 문제가 아니다.** WHATWG URL은 `mongodb:`를 non-special scheme으로 잘 다룬다.
2. **`throw`하는 입력이 정확히 N-10·N-11 대역이다.** 표준 파서에 그대로 위임하면
   레플리카셋(RFC 합법·Atlas 기본)·`$PORT` 보간·백틱·6자리 포트가 **전부 미탐**이 된다.
   `throw`를 "자격증명 없음"으로 해석하면 fail-open이 그대로 재현되고, 규모는 오히려 커진다.
3. **가장 나쁜 것은 N-12다.** URL 파서는 예외를 던지지 않고 **틀린 답을 조용히 준다** —
   `#`이 fragment를 시작해 authority가 `svc:P@ss`에서 끊기고 `pass="P"`, `host="ss"`가 된다.
   이것은 N-12와 **완전히 같은 실패 메커니즘**이다. 즉 표준 파서도 같은 함정에 빠져 있으며,
   위임은 함정을 없애는 것이 아니라 **다른 코드베이스로 옮기는 것**이다.

> `throw`가 F-15를 걸러 준다는 점은 유용하다. URL 파서는 **오탐 억제 보조 오라클**로는 쓸 수 있다.
> 다만 §4.3에서 보듯 그 값어치가 복잡도를 넘지 못한다.

### 4.1 두 안의 불변식

#### 안 1 — 정밀화(현행 노선의 연장): 갈래를 늘려 대역을 메운다

N-13을 닫는 최소 수정은 "lenient 갈래의 `:` 요구를 없앤다" 또는 "`:` 없는 형태용 세 번째 갈래를 만든다"다.

- **불변식**: 없다. 갈래별 진입 조건의 논리곱/논리합이 판정한다.
- **성질**: fail-open 유지. 갈래 진입 조건은 그 자체가 열거이므로 다음 형제 조건이 남는다.
- **N-12→N-13이 정확히 이 안의 실패 사례다.** 8차는 이 안을 택했고 9번째 옆칸을 열었다.

이 안은 **기각을 위해 적는다.** 아홉 번째 라운드가 될 것이라는 근거가 여덟 개 있다.

#### 안 2 — fail-closed 단일 불변식 (권고)

판정 구조를 뒤집는다. **열거가 "탐지"하지 않고 "면제"한다.**

> **불변식.** `mongodb(+srv)://` 스킴 뒤 같은 줄(상한 512자) 안에 `@`가 있으면,
> 스킴 뒤부터 그 `@`까지는 **자격증명 구간이다.**
> 예외는 단 하나 — **자격증명 자리에 내부 공백류가 있으면 산문으로 보고 면제한다.**
> ("자격증명 자리" = 첫 `:` 이후, `:`가 없으면 스킴 뒤 전부. "내부" = 후행 트림 후에도 남는 공백류.)

구현상으로는 현행 `findUserinfoEnd`(`masking.ts:274-315`)에서 **뺄 것만 있다**:

1. **엄격 갈래(`masking.ts:277-286`)를 통째로 삭제한다.** `STRICT_USERINFO_RE`가 사라진다 — 이것이 N-11·N-12가 살던 열거다.
2. **lenient 갈래의 `:` 필수 요구(`:291-292`)를 없앤다.** `credStart = colon >= 0 ? colon+1 : authorityStart`. 이것이 N-13이 살던 조건이다.
3. (선택) `hasHostAfter`(`:270-272`)를 남길지 뺄지 — F-26 정책 결정. §4.4에서 분리해 다룬다.

남는 코드는 20줄이고 판정에 쓰이는 문자 집합은 **`\s` 하나**다.

### 4.3 왜 URL 파서 위임을 권고하지 않는가

안 2에 URL 파서를 얹어 F-23·F-24의 과마스킹을 줄이는 하이브리드를 검토했으나 기각한다.

- F-24(`…@host/db?owner=ops@example.com`)에서 URL 파서는 **정답**을 준다(authority가 `/`에서 끝나므로).
- 그러나 N-12(`svc:P@ss#w0rd@host`)에서는 **오답**을 주고, 오답의 방향이 미탐이다.
- 두 경우를 국소적으로 구별하는 방법이 없다. F-24의 `/`·`?`는 경계 뒤에 있고 N-12의 `#`은 경계 앞에 있는데,
  둘 다 "구조 문자가 문자열 어딘가에 있다"는 동일한 관측만 남긴다.
- "둘 중 더 긴 구간을 택한다"로 안전하게 결합하면 항상 fail-closed 쪽이 이겨 **F-24 개선이 0**이다.
- 결론: **URL 파서가 줄 수 있는 유일한 이득은 F-24/F-23의 과마스킹 완화인데, 안전하게 결합하면 그 이득이 사라진다.**
  위험 비대칭(미탐 > 오탐)에 따라 과마스킹은 감수하는 것이 옳다.

**역방향 정의("호스트가 아닌 것")와 엔트로피/모양 기반도 같은 이유로 기각한다.**
전자는 "호스트란 무엇인가"의 열거를 요구하고 — 그것이 정확히 N-8·N-11이 살던 자리다.
후자는 임계값을 도입하는데, `specs/03 §6` 판정(`T-004:130-136`)에 따르면 새니타이저 임계값은
env로 빼지 않는 형태 규격이어야 하고, 엔트로피 임계값은 **오설정 없이도** 짧은 비밀번호
(`P@ss1!`)를 놓치므로 fail-open을 재도입한다. 단, 엔트로피는 **면제 조건의 보강**으로는
쓸 수 있다(예: 자격증명 자리가 사전 단어 하나뿐이면 면제). 후속 과제 후보이지 이번 안의 일부가 아니다.

### 4.4 안 2가 새로 여는 축 — 정직하게

**① 면제 경로는 여전히 무플래그 통과다 (구조적 한계, 닫히지 않음).**
자격증명 자리에 내부 공백류가 있으면 안 2도 원문을 그대로 통과시키고 플래그를 붙이지 않는다.
F-21(비밀번호 중간 공백)이 이 대역이고, F-18(NBSP·EM SPACE 등 `Zs`는 프로브에서 지우지 않는다)이
그 대역을 넓힌다. 실측:

```
현행/안2 동일: "mongodb://appuser:Str0ng Pass@cluster0.example.net/db"     flags=[]   ← 일반 공백
현행/안2 동일: "mongodb://appuser:Str0ng<U+00A0>Pass@cluster0.example.net/db" flags=[]  ← NBSP
현행/안2 동일: "mongodb://appuser:Str0ng<U+2000>Pass@cluster0.example.net/db" flags=[]  ← EN QUAD
```

(`Cf` 계열은 프로브에서 제거되므로 닫혀 있다 — `<U+200B>` 삽입은 양쪽 모두 마스킹된다. 실측 확인.)

**이것이 안 2의 유일한 fail-open이고, 안 2 안에서는 원리적으로 닫을 수 없다.**
면제 조건을 없애면 F-15가 재발하기 때문이다. 닫으려면 **세 번째 출력 상태**가 필요하다:

> **제안(별도 태스크·G3 인간 승인 필요).** `SanitizeFlag`에 `sanitize-ambiguous`를 추가한다.
> 면제로 통과시킨 구간이 있으면 마스킹하지 않되 **플래그는 붙인다.**
> 그러면 "조용한 통과"가 사라지고 F-18/F-21이 유출에서 **경고**로 강등된다.
>
> 현재는 불가능하다: `packages/contracts/src/common.ts:23`이
> `z.enum(["secret-masked", "injection-suspect"])`로 닫아 뒀고, `specs/02:31`·T-004 F-5가
> "2종 고정, 추가는 스펙 개정 + 기존 레코드 마이그레이션 동반"으로 확정했다.
> **T-004에도 T-007에도 이 결정 권한이 없다.**

**② `:` 없는 형태를 마스킹하므로 F-19의 포기가 철회된다.**
`mongodb://my user@host`류는 여전히 면제(내부 공백)로 걸리지만,
`mongodb://someword@host`처럼 공백 없는 한 단어는 이제 마스킹된다. 오탐 코퍼스 12종에서
신규 오탐은 나오지 않았으나, "호스트만 적고 `@멘션`을 공백 없이 붙이는" 표기가 있으면 걸린다.
**F-23과 같은 축이고 새 축은 아니다.**

**③ F-26(줄 끝 `@`)은 `hasHostAfter`를 빼야 닫힌다 — 별도 결정 항목.**
`MONGO_URL=mongodb://svcuser:PW@`(로그 절단)는 안 2에서도 `hasHostAfter`를 남기면 무플래그 통과다.
빼면 닫히지만 **기존 기대값 3개를 바꿔야 한다**(§4.5). 기대값 변경은 CLAUDE.md
"테스트를 고쳐서 통과시키지 않는다"의 경계선이므로 **인간 비준 항목으로 분리**한다.

### 4.5 구현 난이도와 T-007 일정

폐기용 사본에서 기존 스위트를 그대로 돌린 결과(기준선 = 3 failed / 351 passed):

| 변형                                       | 결과                            | 델타                                 |
| ------------------------------------------ | ------------------------------- | ------------------------------------ |
| 기준선 (현행)                              | 3 failed / 351 passed (354)     | —                                    |
| **안 2 (`hasHostAfter` 유지)**             | **3 failed / 351 passed (354)** | **신규 실패 0**                      |
| 안 2 + `hasHostAfter` 제거 (F-26까지 닫음) | 6 failed / 348 passed (354)     | 신규 실패 3 — **전부 꼬리 `@` 단언** |

신규 실패 3건의 정체:

- `mongo 자격증명 유출 회귀 (T-004 N-10) > 호스트가 없는 @는 경계 후보가 아니다 — 엄격 갈래`
- `… — 관대 갈래`
- `호스트 뒤 문자 전수 (T-004 N-11) > 꼬리 @는 경계가 아니다 — 호스트·경로·쿼리를 보존한다`

셋 다 "꼬리 `@`를 경계로 보지 않는다"는 **정책**을 고정한 단언이고, F-26이 지적한 바로 그 정책이다.
따라서 **기술적 회귀가 아니라 정책 변경**이며 인간 비준이 필요하다.

콜드 성능(64KB 상한, 프로세스마다 첫 호출 1회, 실제 `sanitize()`):

| 입력 모양             | 현행      | 안 2     |
| --------------------- | --------- | -------- |
| `mongodb://` 런       | **183ms** | **97ms** |
| `mongodb://x@a ` 런   | 21ms      | 21ms     |
| `mongodb://a:b@c/` 런 | 59ms      | 60ms     |
| `Bearer ` 런          | 170ms     | 174ms    |

**성능 회귀 없음.** `mongodb://` 런이 절반으로 줄어든 것은 엄격 갈래의 문자집합 스캔(매치마다 최대 512자)이
사라졌기 때문이다. F-11(`collectEdits` 이차 곡선)은 손대지 않았으므로 그대로 남는다.

> 부수 발견(Info): 태스크 파일 6차 표의 "새 최악 231ms(`mongodb://x@a ` 런)"는 현행 트리에서
> 재현되지 않는다. 실측 최악은 `mongodb://` 런 183ms이고 `mongodb://x@a `는 21ms다.
> 7·8차 수정이 프로파일을 바꿨는데 표가 갱신되지 않았다. `masking.ts:638` 주석의 "58ms"도
> 실측 170~183ms와 3배 벌어져 있다(8차 Findings가 이미 지적).

**권고 및 T-007 영향:**

1. **안 2 코어(엄격 갈래 삭제 + `:` 요구 삭제)를 채택한다.** 순 삭제 diff, 기존 단언 변경 0,
   신규 실패 0, 성능 개선. **T-007을 지연시키지 않는다** — 별도 태스크 T-004b로 반나절 규모.
2. **`hasHostAfter` 제거(F-26)는 인간 비준 후 별건.** 기대값 3개 변경을 동반한다.
3. **`sanitize-ambiguous` 플래그(§4.4①)는 계약 변경(G3)이라 스펙 개정이 선행**해야 하고,
   기존 레코드 마이그레이션을 동반한다(T-004 F-5 판정). T-007 이전에 결정만 받아 두고
   구현은 M2 이후로 미룰 수 있다 — 미루는 동안 F-18/F-21 대역은 열려 있다는 사실을
   **리스크 등록부에 올려야** 한다.
4. **프로퍼티 생성기 개편(§3.2 이식)은 안 2와 독립적으로, 그리고 안 2보다 먼저 가치가 있다.**
   생성기가 축4를 만들 수 있게 되면 안 2의 채택 여부와 무관하게 다음 옆칸이 자동으로 잡힌다.
   T-004 F-25가 "다음 라운드가 이 축을 볼 때 프로퍼티에 의존하면 안 된다"고 적은 상태를 해소한다.

### 5.2 `task-loop` 프로토콜 개선 제안

현행 `.claude/skills/task-loop/SKILL.md`는 재시도 한도만 정하고 **재시도의 성격**은 정하지 않는다:

```
PLAN → IMPLEMENT → VERIFY → (실패 시 최대 3회 IMPLEMENT 복귀) → REVIEW → PR
```

T-004는 이 한도를 세 번 넘겼고, 여덟 번 다 "같은 방식으로 한 번 더"였다.
한도를 8로 올리는 것도, 4차에서 강제로 멈추는 것도 답이 아니다 —
**같은 방식을 반복하는 것 자체를 금지**해야 한다.

> **제안 문구 (`## 루프` 아래 신설, `### 4. 게이트` 앞).**
>
> ```markdown
> ### 3.5 접근 전환 규칙 (2회 실패 시 강제)
>
> **같은 게이트가 두 번 연속 실패하면 3회차는 "같은 방식으로 한 번 더"가 될 수 없다.**
> IMPLEMENT 재진입 전에 다음 세 줄을 태스크 파일 `## Findings`에 먼저 적는다:
>
> 1. **불변 성질**: 두 번의 실패에서 **바뀌지 않은 것**은 무엇인가.
>    (판정 근거? 자료구조? 기본 동작이 fail-open인가?)
> 2. **축**: 두 실패의 좌표를 잇는 선은 무엇인가. 그 선 위에 몇 개의 케이스가 더 있는가.
> 3. **전환**: 3회차는 (1)을 **제거**하는 수정이다. (1)을 유지한 채 (2)의 케이스를
>    개별적으로 닫는 수정은 3회차로 인정하지 않는다.
>
> 세 줄을 못 쓰면 그것이 BLOCKED 사유다 — "고칠 방법을 모르겠다"가 아니라
> **"내가 무엇을 반복하고 있는지 모르겠다"**가 멈출 이유다.
>
> 이 레포에는 두 축이 각각 네 번·여덟 번 반복된 전례가 있다(T-004: 비가시 문자 축 F-8→N-2→N-6→N-9,
> mongo 축 N-3→F-15→N-8→N-10→N-11→N-12→N-13). 벗어난 쪽은 열거를 유니코드 범주로 바꾼 축이고,
> 못 벗어난 쪽은 매 라운드 열거를 정확하게만 만든 축이다.
> ```

> **제안 문구 (`### 5. BLOCKED 처리` 보강).** 현행 템플릿에 한 줄 추가:
>
> ```markdown

> BLOCKED 템플릿에 한 줄이 있었으면 5차에서 이미 "열거가 판정한다"가 적혔을 것이다.

### 5.3 검증 프로토콜 개선 제안

검증자는 매 라운드 **새 케이스를 찾는 데는 성공**했다(41종·58종·94자 중 25자).
실패한 것은 **축을 넓히는 것**이다. 세 개의 대역 스윕 표가 한 칸씩 옆으로만 움직인 것이
그 증거다(§2.3). 인계 형식이 케이스 목록이면 구현도 케이스 단위가 된다.

> **제안 1 — 검증 리포트에 "축" 항목을 필수화한다.**
> 현행은 실패 케이스만 인계한다. 다음 두 줄을 필수 항목으로 둔다:
>
> ```markdown
> 축: <이 실패들이 놓인 입력 문법 위치. "비밀번호 안의 문자" 같은 좌표로 쓴다>
> 미탐색 축: <같은 입력 문법의 다른 위치 중 이번에 훑지 않은 것 전부 열거>
> ```
>
> T-004에 적용했다면 6차 리포트에 "미탐색 축: 사용자명 안 / 호스트 뒤 / 스킴 직후 /
> `:` 없는 형태 / 포트 자리 / 쿼리스트링"이 적혔을 것이고, N-11·N-12·N-13이 세 라운드가 아니라
> 한 라운드에 나왔을 것이다. **미탐색 축의 목록은 실패 케이스보다 싸다** — 실행이 아니라
> 입력 문법을 읽기만 하면 된다.

> **제안 2 — "케이스를 닫았다"를 통과 근거로 인정하지 않는다.**
> 검증 통과 조건을 "지적한 N종이 닫혔다"에서 **"지적한 N종이 놓인 축 전체가 닫혔다"**로 바꾼다.
> 축 전체의 정의는 열거가 아니라 **외부 기준**이어야 한다 — 7차 표가 그렇게 했다
> ("열거가 아니라 외부 기준으로 잠근다: ASCII 인쇄 가능 94자 전수"). 그 방향은 옳았고
> 적용된 위치가 한 칸 옆이었을 뿐이다.

> **제안 3 — 프로퍼티 생성기 독립성을 게이트로 만든다.**
> `invisible.ts` 축이 벗어난 결정타는 생성기가 구현 모듈을 **import하지 않게** 된 것이다
> (`property.spec.ts:118-119`). 이를 규칙으로 승격한다:
>
> ```markdown
> **프로퍼티 생성기는 검증 대상 모듈을 import하지 않는다.**
> 생성 조건을 구현의 조건과 같은 표현으로 쓰지도 않는다 — F-17이 그렇게 재발했다
> (하드코딩 목록을 유니코드 속성으로 바꿨지만 표집 조건이 구현 집합과 글자 그대로 같았고,
> 실제로 `\p{Cf}` 29종을 그대로 통과시켰다).
> 표본이 구현보다 **넓다**는 것을 뮤테이션으로 보인다 — 구현을 좁히는 뮤턴트에
> 프로퍼티가 죽어야 한다. 안 죽으면 그 생성기는 구현에서 역산돼 있다.
> ```
>
> 이 게이트를 지금 `sanitize.property.spec.ts`에 적용하면 mongo 프로퍼티는 **즉시 불합격**이다:
> 호스트가 상수(`:450`)고 `:`가 리터럴이며 `mongoCredentialArb`의 알파벳이
> `[A-Za-z0-9_-]`(`:36, :102`)로 구현의 안전 영역 안에 있다.

이 문서는 `docs/analysis/` 아래 마크다운 한 파일만 추가한다. 코드·테스트·스펙 변경 없음.

`git status --porcelain`로 확인했다 — 남은 변경은 §0의 T-007 워킹트리 잔여물뿐이다.

`pnpm verify`는 §0에서 밝힌 이유로 **이 문서 작성 전부터 그린이 아니다.**
문서 작성 후 실행 결과는 **G1(lint)에서 조기 실패**한다:

```
> eslint .
packages/core/src/db/records.ts
  86:29  error  '_ignored' is assigned a value but never used  @typescript-eslint/no-unused-vars
✖ 1 problem (1 error, 0 warnings)
```

`packages/core/src/db/records.ts`는 **untracked T-007 파일**이다. 이 문서는 마크다운 한 파일만
추가했고 eslint 대상이 아니다(리포트에 등장하지 않는다). 따라서 이 실패는 이 작업과 무관하다.
lint에서 멈추므로 유닛·통합 단계는 실행되지 않았다 — §0의 3 failed / 351 passed는
`vitest run packages/core/src/sanitizer`를 직접 돌려 얻은 수치다.

**추가 관측(Info).** 이 문서를 쓰는 동안 워킹트리의 untracked 파일이 1개(`db/records.ts`)에서
9개로 늘었다(`packages/api/src/{auth,cursor,embed-jobs,errors,record-fields,records,sanitize-record,summary}.ts`).
`feat/T-004-sanitizer` 브랜치에서 T-007 구현이 **동시 진행 중**이다.
