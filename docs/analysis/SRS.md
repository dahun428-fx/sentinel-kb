# 소프트웨어 요구사항 명세서 (SRS)
**시스템**: sentinel-kb — AI-First 트러블슈팅 지식 보관소
**문서 버전**: 1.0 | **표준**: ISO/IEC/IEEE 29148 구조 준용

---

## 1. 서론

### 1.1 목적
본 문서는 sentinel-kb의 기능·비기능 요구사항을 정의한다. 개발자, 검토자, 그리고 **구현을 수행하는 AI 에이전트**가 동일한 요구사항을 참조하도록 하는 것이 목적이다. 본 문서의 요구사항 ID는 설계·테스트·추적성 매트릭스(RTM)에서 그대로 참조된다.

### 1.2 범위
sentinel-kb는 여러 소프트웨어 프로젝트에서 발생한 **트러블슈팅 사례**와 **AI 개발 이격(divergence)** 을 축적하고, 자연어·에러 텍스트로 검색해 과거 해결 절차를 제공하는 지식 보관소다.

| 포함 | 제외 |
|---|---|
| 지식 레코드 등록·검색·조회 | 실시간 로그 수집·APM |
| MCP 서버를 통한 에이전트 접근 | 알림·온콜 스케줄링 |
| RAG 기반 원인 가설·해결 절차 제안 | 티켓팅 워크플로 |
| 읽기 전용 웹 UI | 다국어 UI |

### 1.3 용어 정의
| 용어 | 정의 |
|---|---|
| 레코드(Record) | 지식의 최소 단위. `incident` 또는 `divergence` |
| 이격(Divergence) | AI 에이전트 산출물이 의도·스펙과 벌어진 사건 |
| 청크(Chunk) | 레코드의 섹션 단위 분할물. 임베딩·검색의 단위 |
| RRF | Reciprocal Rank Fusion. 벡터·키워드 검색 결과 융합 기법 |
| 그라운딩(Grounding) | 생성된 문장이 검색된 근거를 인용하고 있는 상태 |
| MCP | Model Context Protocol. 에이전트가 외부 도구에 접근하는 프로토콜 |
| 프로젝트 스코프 | 인증 키에 부여된 소속 프로젝트. 쓰기 권한의 경계 |

### 1.4 참조 문서
`specs/00~07`, `docs/analysis/USE-CASES.md`, `docs/design/SAD.md`, `docs/test/TEST-PLAN.md`

## 2. 전체 설명

### 2.1 제품 조망
독립 시스템이며 외부 의존은 MongoDB Atlas, 임베딩 API, LLM API 세 가지다. **1차 인터페이스는 MCP 서버**이고 웹 UI는 보조 클라이언트다. 이 우선순위가 전체 설계를 지배한다.

### 2.2 사용자 특성
| 액터 | 유형 | 특성 |
|---|---|---|
| A1 대응 에이전트 | 시스템(AI) | 토큰 예산에 민감. 도구 설명만으로 호출 여부를 판단 |
| A2 기록 개발자 | 사람 | 장애 처리 직후 기록. 기록 비용이 높으면 안 남긴다 |
| A3 열람자 | 사람 | 웹 UI로 과거 사례 탐색 |
| A4 운영자 | 사람 | 키 발급, 골든셋 승인, 배포 |

### 2.3 제약 조건
| ID | 제약 |
|---|---|
| CON-01 | 임베딩·LLM 호출 비용이 유한하므로 실모델 호출은 eval 계층으로 한정 |
| CON-02 | Atlas Search는 로컬 에뮬레이터가 없어 벡터 관련 통합 테스트는 테스트 클러스터 필요 |
| CON-03 | 단일 EC2 인스턴스 운영. 서버는 stateless여야 함 |
| CON-04 | MCP 도구 개수는 5개로 제한 (에이전트 인지 부하) |

### 2.4 가정 및 의존성
- 각 프로젝트의 에이전트 하네스(CLAUDE.md 등)에 호출 프로토콜을 삽입할 수 있다.
- 기록자는 장애 직후 5분 이내에 기록을 남길 의사가 있다.
- 임베딩 모델은 교체될 수 있다(버전 관리 필요).

## 3. 기능 요구사항

각 요구사항은 `입력 → 처리 → 출력` 형식으로 기술한다. 검증 방법은 RTM 참조.

### FR-01 레코드 등록·수정·조회
- **입력**: 레코드 타입(incident|divergence), 제목, 심각도, 태그, 타입별 섹션 필드
- **처리**: 스키마 검증 → 새니타이즈(FR-06) → `project`를 인증 키에서 주입 → 저장 → 요약 생성 → 인제스트 잡 등록
- **출력**: 레코드 ID, 새니타이즈 플래그, 경고 메시지
- **규칙**: 클라이언트가 보낸 `project` 값은 무시한다. 쓰기는 자기 프로젝트로만 가능하다.

### FR-02 인제스트 파이프라인
- **입력**: 인제스트 잡(레코드 ID)
- **처리**: 섹션 단위 청킹 → 배치 임베딩 → 청크 upsert(멱등). 실패 시 재시도 3회 후 dead 처리
- **출력**: 청크 레코드
- **규칙**: 인제스트 실패가 레코드 저장을 롤백해서는 안 된다.

### FR-03 하이브리드 검색
- **입력**: 질의 문자열, 선택적 필터(type, project), 결과 수
- **처리**: 질의 임베딩 → 벡터 검색 + 키워드 검색 → RRF 융합 → 레코드당 최대 2청크로 정리
- **출력**: 상위 결과 목록 (레코드 ID, 제목, 요약, 섹션, 점수, 플래그)
- **규칙**: 응답에 레코드 본문 전체를 포함하지 않는다.

### FR-04 RAG 답변 생성
- **입력**: 에러 텍스트 또는 질의
- **처리**: 검색 → 유사도 임계값 판정 → (충족 시) 인용 강제 프롬프트로 생성 → 인용 후처리 검증
- **출력**: 원인 가설·해결 절차 + 인용된 레코드 ID 목록, 또는 `미발견` 응답
- **규칙**: 임계값 미달 시 LLM을 호출하지 않고 기록을 권유한다. 근거 없는 해결책 생성은 금지다.

### FR-05 MCP 서버
- **입력**: MCP 클라이언트의 도구 호출 (Bearer 인증)
- **처리**: 인증·스코프 해석 → core API 위임 → 응답 정규화(요약화·데이터 래핑)
- **출력**: 도구별 응답
- **규칙**: 도구는 정확히 5개. 검색 응답은 토큰 예산을 초과하지 않는다.

### FR-06 새니타이즈 게이트
- **입력**: 저장 대상 텍스트
- **처리**: 자격증명 패턴 마스킹, 프롬프트 인젝션 의심 패턴 탐지·표시
- **출력**: 정제 텍스트 + 플래그 목록
- **규칙**: 마스킹 사실을 사용자에게 알린다. 인젝션 의심 텍스트는 삭제하지 않고 표시만 한다.

### FR-07 피드백 수집
- **입력**: 레코드 ID, 도움 여부, 메모
- **처리**: 저장 → 골든셋 **후보**로 적재
- **출력**: 접수 확인
- **규칙**: 사람 승인 없이 골든셋으로 승격되지 않는다.

### FR-08 웹 열람 UI
- **입력**: 검색어, 필터
- **처리**: core API 호출
- **출력**: 결과 목록·상세 화면, 인용 링크 이동
- **규칙**: 인증 키는 서버 측에서만 사용한다.

### FR-09 (P2) 포스트모템 위저드 · 재발 패턴 대시보드
본 릴리스 범위 밖. 백로그로 유지한다.

### FR-10 초기 데이터 구축
50건 이상의 시드 레코드(사례 40 + 이격 10)를 확보한다. 외부 공개 자료는 원문을 복제하지 않고 요약·출처 표기한다.

## 4. 비기능 요구사항

| ID | 분류 | 요구사항 | 측정 |
|---|---|---|---|
| NFR-01 | 성능 | 검색 API p95 < 1.5s, MCP 도구 p95 < 2s | 부하 스크립트 |
| NFR-02 | 정확성 | 근거 없는 해결책 생성 0건 | 임계값 시나리오 eval |
| NFR-03 | 효율 | MCP 검색 응답 ≤ 약 800 토큰 | 토크나이저 근사 테스트 |
| NFR-04 | 보안 | 모든 외부 표면 Bearer 인증, 프로젝트 스코프 강제 | 통합 테스트 |
| NFR-05 | 보안 | 저장 콘텐츠 경유 간접 프롬프트 인젝션 방어 | 레드팀 eval 10/10 |
| NFR-06 | 유지보수 | 임베딩 모델 교체 시 무중단 마이그레이션 가능 | 마이그레이션 리허설 |
| NFR-07 | 가용성 | 인스턴스 소실 시 데이터 무손실, 재기동으로 복구 | 복구 훈련 |
| NFR-08 | 품질 | 검색 Recall@5 ≥ 0.85, 도구 선택 정확도 ≥ 0.9, 인용률 100% | eval 리포트 |

## 5. 인수 기준 (릴리스 게이트)
1. NFR-08의 세 지표를 모두 충족한다.
2. 인젝션 레드팀 10건 전부 방어한다.
3. 서로 다른 두 프로젝트의 에이전트가 동일 지식 보관소로 문제를 해결하는 시나리오가 재현된다.
4. 4주간 실사용 기록 30건 이상, 검색 적중 사례 5건 이상이 확보된다.
