검토일: 2026-10-21

## 총평

**문서의 기본 설계는 좋다. 다만 지금은 문서를 더 늘리기보다, 기존 문서의 기준과 상태를 맞춰야 한다.**

`UPLIFT-PLAN.md`는 “많이 구현했지만 아직 쓰지 않는다”는 실제 문제를 잘 잡았다. 기능 확장보다 로컬 실행 → 실 임베딩 → 실제 사례 → 품질 측정 → 도그푸딩을 앞세운 방향도 적절하다. M7 확장을 보류한 판단을 유지하는 편이 좋다.

반면 실행의 기준이 되는 숫자, 외부 데이터 전송 설명, 이미 해결된 차단 사유가 서로 맞지 않는다. 이 상태에서 에이전트에게 다음 작업을 맡기면 문서 선택에 따라 다른 목표와 선행 조건을 적용할 수 있다. **현재 플랜은 방향을 공유하기에는 충분하지만, 그대로 자동 실행하기에는 보완이 필요하다.**

문서·스펙과 관련 구현을 대조한 정적 리뷰다. 테스트·서비스·eval은 실행하지 않았고, GitHub의 현재 상태나 외부 프로젝트 원문도 다시 확인하지 않았다. 계획에 기재된 과거 테스트 통과 수치와 원격 상태는 이번 리뷰에서 재인증한 결과가 아니다.

## 잘 짜인 부분

- **목표와 제외 범위가 명확하다.** 개인 실사용을 1차 목표로 두고, 하네스 개선·아티클 확장을 제외했다. 당장 필요한 제품 루프에 집중할 수 있다.
- **확인된 사실과 미검증 상태를 구분한다.** 로컬/CI 검증을 구분하고, `기록 없음`을 `미완료`와 동일시하지 않는다. 문서의 신뢰도를 높이는 좋은 방식이다.
- **순서의 이유가 있다.** P4~P6의 배치와 배포를 뒤로 미룬 근거가 적혀 있어, 이후 조건이 바뀌면 순서도 다시 판단할 수 있다.
- **결정과 질문을 분리했다.** D/F/Q 식별자 덕분에 결정 근거와 미해결 항목을 추적하기 쉽다.
- **분석 → 설계 → 태스크 → 테스트의 연결이 있다.** SRS, SAD, RTM, 태스크 스펙이 분리돼 있고, RTM은 web 인증의 부분 충족도 명시한다. 틀을 새로 만들 필요는 없다.

## 우선 수정할 사항

### 1. 높음 — 로컬 저장을 외부 전송 없음으로 설명한다

근거:

- [UPLIFT-PLAN.md:184](../plan/UPLIFT-PLAN.md#6-결정-대기): Q-1 권장안에 “회사 문서가 맥북 밖으로 나가지 않는다”.
- [UPLIFT-PLAN.md:144](../plan/UPLIFT-PLAN.md#4-우선순위): P4에서 Voyage 실 임베딩을 사용한다.
- `packages/core/src/embedder/voyage.ts:23,125–131`: 외부 Voyage 엔드포인트로 `input: batch`를 전송한다.

DB가 atlas-local이어도 임베딩할 텍스트는 외부 API로 나간다. 따라서 실행 위치 Q-1만으로 회사 문서의 외부 전송 여부를 판단할 수 없다. sanitizer가 비밀 문자열을 지워도 회사 문서의 모든 비공개 내용을 제거한다고 볼 근거는 없다.

**권장 수정:** Q-1 설명을 “DB 원문은 로컬에 저장되지만, 임베딩 입력은 Voyage로 전송된다”로 고친다. P5 선행 조건으로 외부 전송 가능한 자료의 범위를 정한다. 답변 생성·아티클 생성도 활성화한다면 해당 LLM 전송 경로를 같은 표에 추가한다.

데이터 흐름 표는 `원문 → sanitizer → 청크 → 임베딩 API → 로컬 DB` 정도면 충분하다. 개인 공개 자료와 회사 비공개 자료의 허용 범위를 구분해야 한다.

SRS의 NFR-08도 검색 0.85, 도구 선택 0.90을 요구한다. 낮은 수치가 중간 마일스톤이고 높은 수치가 최종 목표라면 함께 존재할 수 있지만, 현재 문서에는 그 구분이 없다. 예를 들어 Recall@5 0.82는 P6 통과지만 제품 목표에는 미달한다.

**권장 수정:** 지표마다 `중간 진입 기준 / 실사용 승인 기준 / 회귀 기준선`을 구분한다. 중간 기준 0.80을 유지한다면 “제품 목표 0.85 충족을 뜻하지 않는다”는 점과 다음 평가 시점을 명시한다. 스펙 변경이 필요하면 기존 승인 절차에 따라 결정 기록을 남긴다.

2. **오래된 차단 사유 정리:** seedManifest 반영, SRS의 로컬 검증 설명, 해결된 PR 스택을 갱신한다.
3. **문서 진입점 연결:** docs 색인에서 UPLIFT로 안내하고 기존 계획에는 역사적 역할을 표시한다.
4. **완료 기준 보강:** P4 적재 커버리지, P6 기능별 평가, P7 계측 스모크 검증을 추가한다.

각 실행 항목은 `선행 조건 / 완료 증거 / 실패 시 중단 조건 / 후속 태스크` 네 가지가 있으면 충분하다. 새 계획 문서를 더 만들기보다 UPLIFT의 완료 기준과 기존 문서의 상태를 맞추는 작업이 먼저다.

- 프로젝트의 Markdown 파일 96개를 목록화했다. 모든 파일을 문장 단위로 정독한 전수 심사는 아니다.
- UPLIFT 전반과 문서 색인, 실행 계획, WBS, 결정 대기 목록, 제품·테스트·배포 스펙을 중심으로 검토했다.

- 기존 코드·계획·스펙은 수정하지 않았다. 이 리뷰 문서만 추가했다.
